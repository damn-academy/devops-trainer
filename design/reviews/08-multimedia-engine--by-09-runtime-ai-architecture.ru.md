# Рецензия на 08 «Движок интерактивного учебника» — от роли 09 (архитектура сред исполнения и ИИ)

Рецензент: автор `09-runtime-ai-architecture.md`. Дата: 18.11.2026. Рецензируемая версия: 08, версия 1 от 18.11.2026. Сверялся с 01–07, 09, 10 и с требованиями владельца R1–R12.

## Вердикт

Как движок документ сильный. Разбор Sankofa точный, есть ленивые чанки, раздельный экран «терминал + схема», правило «состояние, а не текст команды», доступность по WCAG 2.2 и бюджеты в CI. Шина `SimEvent` и интерфейс `WidgetInstance` уже стоят у меня в 09 (§1.3, §1.5), и менять их я не предлагаю. В нынешнем виде документ всё же нельзя принимать как основу контента. На то пять причин, каждая блокирующая:

1. Визуальный язык построен на туши, метафорах и персонажах. R4 и R5 это прямо запрещают.
2. Степпер проигрывает записанную ленту событий и не умеет пересчитывать процесс, когда ученик меняет параметр. А это и есть главная механика R4.
3. Формат урока (`glossary.yaml`, строковые id, `scenes`, `beginner/intermediate/experienced`, `requires`) расходится с графом понятий из 01 (`concepts.yaml`, `L17`/`D03`, `screens`, `L0/L1/L2`, `uses`, правило «одно понятие на экран»).
4. Флагман 6.1 вводит namespaces, cgroups, capabilities и chroot в блоке Docker. По R6 всё это должно прийти раньше, в блоке Linux.
5. Все четыре флагмана дублируют интерактивы из 03, 04 и 05 и в нескольких местах им противоречат.

Сверх того, в документе нет лестницы документации (R2), нет каталога объяснений для каждого блока (R3), нет виджетов для многоузловой сети (R11) и для реального этапа (R12). Ниже по каждому пункту готовый текст для вставки.

Итого: 6 BLOCKING, 14 MAJOR, 8 MINOR.

### 2. BLOCKING — Степпер не пересчитывает процесс при смене параметра (R4)

**Где:** §3.1, §3.5, §7.6.

**Что не так.** Шаги степпера берутся либо из YAML-сценария, либо из записи живой сессии, то есть это свёртка **фиксированной** ленты событий. R4 требует, чтобы смена параметра (replicas, memory limit, TTL, TCP window) **сразу** пересчитывала процесс и рядом объясняла, что изменилось. Записанная лента так не умеет: при TTL=0 в ней не появятся новые запросы к корню. Тумблер «сломай» в §3.5 «перезапускает текущий шаг сценария», но сценарий, который пришёл из записи, после поломки остаётся прежним.

**Исправление.** Добавить в §3 новый примитив и сделать его основой `stepper`:

```ts
// web/src/engine/process-model.ts
export interface ParamSpec {
  id: string;                         // 'ttl', 'replicas', 'memory.max', 'tcp.window'
  label: Bi;
  kind: 'range' | 'toggle' | 'choice';
  min?: number; max?: number; step?: number; unit?: string;   // '512Ki', 's'
  options?: { id: string; label: Bi }[];
  default: number | boolean | string;
}
export interface Step {
  id: string; label: Bi;               // короткая подпись на таймлайне: 'SYN'
  at: number;                          // модельное время, мс
  events: SimEvent[];                  // что меняется на схеме (та же шина)
  caption: Bi;                         // одна фраза «что произошло»
  focus: string[];                     // id узлов и рёбер, которые подсветить
}
export interface ProcessModel<P = Record<string, unknown>> {
  id: string;
  params: ParamSpec[];
  breaks: { id: string; label: Bi; remove: string[] }[];    // «сломай»: какие узлы/рёбра выключаются
  run(p: P, broken: string[]): Step[];                     // чистая функция, детерминированная, Vitest
  explainDelta(prev: Step[], next: Step[], changed: string): Bi;  // «TTL 0 → ответ не кешируется: шаги 3–5 повторяются при каждом запросе»
}
```

Правила для §3.1:

1. Таймлайн — это `run(params, broken)`. При изменении параметра модель пересчитывается за ≤ 16 мс. Степпер остаётся на шаге с тем же `id`, а если такого шага больше нет — на ближайшем по `at`.
2. Справа от схемы — панель «Что изменилось» с текстом `explainDelta` и разницей шагов (появились или исчезли, плюс разница во времени: «Connect: 1 RTT → 0, соединение переиспользовано»).
3. «Сломай» — тот же параметр: `broken` убирает узлы и рёбра, модель строит процесс без них, обрыв рисуется на месте с подписью.
4. Записанная лента живой сессии остаётся отдельным источником (`source: recording`), но параметров у неё нет. Ползунки в таком режиме неактивны и подписаны: «это запись вашей сессии; чтобы менять параметры, откройте модель».
5. Модель обязана совпадать с симулятором. CI прогоняет `run(default)` и запись симулятора на том же сценарии и сравнивает последовательности событий. Это продолжение правила §7.6 и «золотых записей» из 09 §1.3.

В §7.6 добавить поле `model: models/dns-resolve.ts` как альтернативу `steps:`. В YAML урока параметры перечисляются, а не программируются:

```yaml
- widget: stepper
  model: dns-resolve
  params: { ttl: { default: 300, min: 0, max: 86400 }, cache: { default: true } }
  breaks: [authoritative-down, wrong-a-record]
```

### 4. BLOCKING — Изоляция ядром введена в Docker, а не в Linux (R6)

**Где:** §6.1 целиком; строка «Требует введённых в блоке Linux терминов: процесс, PID… /proc».

**Что не так.** По R6 namespaces (`unshare`, `nsenter`, `/proc/<pid>/ns`, `lsns`), cgroups v2 (`memory.max`, `cpu.max`, `pids.max`, OOM), capabilities (`capsh`, `getcap`/`setcap`), mount/chroot/overlayfs, seccomp, а также процесс против потока (`/proc/<pid>/task`, `ps -eLf`) вводятся в **Linux**, и для всех уровней. 6.1 вводит их в блоке Docker, причём сцены 2–7 — это урок Linux. В 01 D03 стоит в группе Docker, но требует N21; в 02 §5.1 namespace и cgroup появляются только в L16 и только для С/О. Значит, новичок приходит в Docker без этих понятий, и R6 нарушен в трёх документах сразу. Решать это должен 08: он владеет флагманом, а 01 и 02 за ним последуют.

### 14. MAJOR — Фактические ошибки в 6.1

**Где:** 6.1/3, 6.1/5, 6.1/6, 6.1/9, §5.2 (`--c-ns-*`).

1. «Семь ссылок» в `ls -l /proc/$$/ns`. На ядре 6.12 (`dt-kernel`, 09 §1.4) их 10: `cgroup, ipc, mnt, net, pid, pid_for_children, time, time_for_children, user, uts`. 3. cgroup: последовательность неполная. Нужно `mkdir /sys/fs/cgroup/demo`. Контроллер memory должен быть включён у родителя (`echo +memory > /sys/fs/cgroup/cgroup.subtree_control`), а без systemd в образе `lab-alpine` он по умолчанию не включён. 4. `chroot` «можно выйти». Выйти может только процесс с `CAP_SYS_CHROOT` (root). Уточнить: «root внутри chroot может выйти (классический приём с вложенным chroot и `..`); `pivot_root` в новом mount namespace меняет корень всего пространства, и старый корень можно отмонтировать». ### 15. MAJOR — Фактические ошибки в 6.3 (сети)

1. 6.3/2: «вывод `+trace` построчно совпадает со стрелками» к рекурсивному резолверу. `dig +trace` делает итеративное разрешение **сам**, от машины ученика к корню, TLD и авторитативному серверу; рекурсивный резолвер провайдера и его кеш в трассе не участвуют (только для первоначального запроса NS корня). Поэтому ползунок «через 30 с / через 2 ч» с `+trace` не показывает кеш. Исправить: две отдельные дорожки — «как спрашивает резолвер» (модель; кеш и TTL — ручки) и «как это повторяет `dig +trace`» (без кеша); кеш резолвера видно через `dig @resolver name` дважды: уменьшающийся TTL во втором ответе.
2. 6.3/7, TLS 1.3: порядок «сертификат → проверка цепочки → общий ключ → Finished» — это схема TLS 1.2. В 1.3 общий секрет выводится сразу после ServerHello (`key_share`), а `EncryptedExtensions`, `Certificate`, `CertificateVerify`, `Finished` сервера идут **уже зашифрованными** (RFC 8446 §2). Подправить шаги степпера и отметить на конверте, с какого шага содержимое закрыто.
3. 6.3/6: «firewall молча дропает — секундомер до `Connection timed out`». У curl тайм-аут соединения по умолчанию 300 с, а ядро Linux сдаётся после `tcp_syn_retries=6` (около 127 с). В симуляторе показывать реальную лестницу повторов SYN (1, 2, 4, 8… с) и подсказывать `--connect-timeout`. Так уже сделано в 03 §7.1.
4. §3.6 и 6.3/5–6: на маршрутизаторе меняется не только IP при NAT. На **каждом** L3-хопе снимается и надевается новый Ethernet-конверт (новые MAC), TTL уменьшается на 1, пересчитывается контрольная сумма (03 §7.2 экран 3). 5. §3.6: пример `dst 93.184.215.14:443` нарушает собственное правило §5.3 п. 5 (адреса из RFC 5737), да и адрес example.com давно сменился. Заменить на `198.51.100.20`.

Терминал — своя тема xterm на токенах: фон `--c-term-bg` (глубокий графит в обеих темах), ANSI-цвета приглушены до той же палитры, курсор-блок, Plex Mono 14 px, line-height 1,35; приглашение раскрашено (`user@host:path$`) теми же токенами, что «пользователь» и «ядро» на схемах. Переход между шагами — 240 мс, `cubic-bezier(.2,.7,.2,1)`; в спокойном режиме 0 мс.

### 23. MINOR — Опытный уровень «видит только механизм, лабораторию и проверку»

**Где:** §4, абзац про уровни.

**Что не так.** По R1 ядро продукта — связная теория и строгий порядок для всех. Опытный программист не знает cgroups и сетевого стека Kubernetes, и скрытие теории оставит дыры. Кроме того, по R2 опытный начинает со ступени 3 лестницы документации, а этого в §4 нет.

**Исправление.** «Опытный видит теорию в сжатом виде (экраны с `levels: [L0]` свёрнуты в строку, экраны теории `theory` сокращены до абзаца-резюме с кнопкой "полностью"), начинает с задачи-вызова (01 §7, L2) и со ступени 3 лестницы документации».

### 24. MINOR — Экраны §4 без вида «теория»

### 25. MINOR — Мелкие неточности в 6.2

1. 6.2/2: `tar -tzf blobs/sha256/<слой>`. Слои в `docker save` бывают несжатыми (классическое хранилище) или сжатыми (containerd image store), поэтому `-z` то работает, то падает. Писать `tar -tf` (GNU tar и busybox распознают сжатие сами) или сначала `file blobs/sha256/<слой>`.
2. 6.2/1: «`EXPOSE`/`CMD` листа не рождают». Верно по слоям, но в `docker history` эти инструкции видны строками размером 0B. Сказать это явно, иначе вывод `history` «не совпадёт со стопкой».
3. `FROM alpine:3.20` → `alpine:3.22`, как в 04 §5.2.
