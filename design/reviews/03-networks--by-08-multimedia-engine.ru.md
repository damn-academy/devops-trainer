## 1. BLOCKING — v86 отвергнут, многоузловой стенд с собственным коммутатором отсутствует (R11)

**Где:** §2, таблица продуктов (строка v86), «Решение 1», «Решение 4», §7.3.5.

**Что не так.** Документ пишет, что v86 — это «одна VM — десятки МБ; три-пять машин в топологии на ноутбуке неприемлемо; пакеты между VM нельзя анимировать и детерминированно ломать». Третий тезис неверен. В v86 каждый кадр Ethernet гостя выходит событием шины `net0-send` (Uint8Array), а принимается через `bus.send("net0-receive", frame)` (см. `examples/two_instances.html` в репозитории v86). Значит, коммутатор на JS видит каждый кадр. Он может разобрать кадр нашими же диссекторами (§8.1), анимировать, задержать, отбросить, обрезать по MTU и записать в pcap. Первый тезис снят R11: Alpine-узел на 64–128 МБ, 3–4 узла на ноутбуке, 1 на телефоне.

Есть и расхождение с 09. Там сеть машин — `inbrowser` (BroadcastChannel), то есть общий «хаб» без топологии. Такой хаб нельзя ни нарисовать по линкам, ни поломать по одному линку. R11 требует собственный коммутатор, поэтому в 09 надо заменить `inbrowser` на `vswitch`. Это замечание к 09, но решение должен зафиксировать блок «Сети».

**Исправление. Вставить новый раздел 7.7 и переписать «Решение 1» и «Решение 4».**

> **Решение 1 (новая редакция).** Сеть живёт на двух ярусах с одной моделью пакета.
> Ярус A — `netlab` (TypeScript, моделируемое время, полный детерминизм). Он нужен новичку, для теории, для пошаговых объяснений и для сценариев с моделируемыми часами.
> Ярус B — 2–4 настоящих Linux-узла в v86 (образ `lab-alpine`/`lab-net`, по 64–128 МБ), соединённые нашим коммутатором `vswitch` на JS. Он нужен для ARP, маршрутизации, iptables/nftables, NAT, WireGuard и tcpdump на настоящем ядре.
> Обе среды отдают в шину 08/3.0 одни и те же события `net.packet` с одним форматом `Packet` (§8.1). Поэтому схема, аниматор и пакетоскоп не знают, на каком ярусе работает урок.

> ### 7.7. Многоузловой стенд: v86 + `vswitch`
>
> **Устройство.** Каждый узел — отдельный Web Worker с экземпляром v86, `net_device: { type: "virtio" }` без `relay_url`. Воркер подписан на `net0-send` и пересылает кадр в воркер коммутатора через `MessagePort`, передавая `ArrayBuffer` как transferable. Коммутатор отдаёт кадр нужному узлу, а тот выполняет `bus.send("net0-receive", frame)`. Коммутатор — обучающийся L2-мост: таблица MAC с таймером старения 300 с, рассылка неизвестного во все порты, опционально 802.1Q (порт access/trunk, VLAN ID) для карточки VLAN в каталоге протоколов.
>
> ```ts
> // web/src/runtime/vswitch.ts
> interface LinkParams { delayMs: number; jitterMs?: number; lossPct?: number; mtu?: number; bandwidthKbps?: number; up: boolean }
> interface VSwitch {
>   attach(port: string, endpoint: FramePort): void;            // FramePort: v86-воркер или хост netlab
>   link(port: string, p: Partial<LinkParams>): void;           // ползунки «задержка/потери/MTU» на схеме
>   vlan(port: string, mode: { access: number } | { trunk: number[] }): void;
>   fault(rule: { port?: string; match: string; action: 'drop' | 'delay' | 'corrupt'; ms?: number }): string; // match — подмножество pcap-filter
>   tap(port: string): ReadableStream<Packet>;                  // «щуп» = tcpdump на линке, экспорт pcap linktype 1
>   mac(): { mac: string; port: string; age: number }[];        // таблица MAC — рисуется на схеме
> }
> ```
>
> **Смешанные топологии.** Хост `netlab` тоже может быть портом коммутатора, потому что он генерирует настоящие байты с контрольными суммами. Так «интернет» из §7.3.2 (корневые, TLD и авторитативные DNS, публичные резолверы) обслуживает настоящие v86-узлы, и нам не нужно держать четвёртую виртуальную машину под DNS. Ограничение: TCP-стек netlab упрощённый (фиксированное окно, без SACK и congestion control). Поэтому в смешанной топологии хост netlab отвечает только на ARP, ICMP, DHCP и DNS по UDP. TCP-концы всегда находятся в v86 (nginx, приложение, sshd в `lab-net`). Это правило проверяет валидатор лабораторий.
>
> **Анимация и поломка.** Каждый кадр, прошедший через коммутатор, становится событием `net.packet {from, to, layers, verdict}`. Аниматор 08/3.6 рисует его по ребру схемы, в полёте одновременно не больше 6 конвертов, остальные складываются в счётчик на линке. Поломки детерминированы на уровне коммутатора («линк r1–h2 down», «MTU 1400 на линке wg», «отбрасывать ICMP type 3 code 4»). Тайминги внутри гостей не детерминированы, поэтому проверки на ярусе B строятся только по фактам (09, §2) и никогда по времени.
>
> **Ядро.** К фрагменту `dt-kernel` из 09 §1.4 добавить: `CONFIG_WIREGUARD`, `CONFIG_VXLAN`, `CONFIG_VLAN_8021Q`, `CONFIG_GENEVE` (для О), `CONFIG_NET_SCH_NETEM`, `CONFIG_IP_ADVANCED_ROUTER` + `CONFIG_IP_MULTIPLE_TABLES` (для `ip rule`), `CONFIG_NF_CONNTRACK_NETLINK` + `CONFIG_NF_CT_NETLINK` (утилита `conntrack`), `CONFIG_NETFILTER_XT_MATCH_STATISTIC`, `CONFIG_NETFILTER_XT_MARK`, `CONFIG_NETFILTER_XT_MATCH_ADDRTYPE`, `CONFIG_NFT_NUMGEN` (правила kube-proxy, см. замечание 10). В `lab-net` добавить `wireguard-tools`, `tcpdump`, `conntrack-tools`, `iproute2-tc`.
>
> **Бюджеты приёмки (спайк фазы 0).**
>
> | Что | Порог |
> |---|---|
> | 3 узла `lab-alpine` по 96 МБ, память вкладки | ≤ 1,2 ГБ |
> | Время до трёх приглашений из снимков (повторный визит) | ≤ 8 с |
> | `ping` между узлами через `vswitch`, RTT при нулевой заданной задержке | ≤ 5 мс |
> | `iperf3` между узлами (для объяснения про окно TCP) | ≥ 20 Мбит/с |
> | Телефон / `deviceMemory < 4` | 1 узел, остальные — хосты netlab |
>
> **Какие уроки идут на ярусе B.** Н: N3 и N4 по выбору («то же на настоящем Linux»). С и О — обязательно: N9 NAT, N10 netfilter, N14 WireGuard, новый N16 «Сеть внутри одной машины» (замечание 4), сценарии T2, T8, T9, T10, все задания ступеней 4–5 лестницы документации (замечание 2) и «трудный режим» части А экзамена.
>
> **Мост к Kubernetes (R11).** Тот же `vswitch` соединяет узлы гибридного кластера 05: control plane в kube-lite, агент-kubelet и `crun` в v86. Межузловая сеть подов — настоящий VXLAN (`ip link add vxlan0 type vxlan id 42 dstport 4789 dev eth0`) поверх нашего коммутатора. Ученик сначала собирает его руками в карточке VXLAN (замечание 3), а потом узнаёт в CNI.

Таблицу продуктов в §2 поправить так: строка v86, колонка «Что берём» — «ярус B блока, многоузловые лаборатории через `vswitch`»; колонка «Почему не основа» — «недетерминированные тайминги; поэтому теория и сценарии с моделируемым временем остаются в netlab».

> ### 7.9. Каталог протоколов
>
> Принцип каталога и всего блока: **любая сетевая проблема привязана к уровню**. Каждая карточка начинается с плашки уровня цветом `--c-l2…--c-l7` и заканчивается разделом «как ломается» с вопросом «какой уровень сломался?».
>
> **Формат карточки (YAML, `content/net/protocols/<id>.yaml`):**
> ```yaml
> id: proto-dns
> level: beginner                 # beginner | intermediate | experienced
> layer: L7                       # L2 | L3 | L4 | TLS | L7; для туннелей — layer: L3 over L4
> transport: [udp/53, tcp/53]
> introduced_in: N8               # модуль, после которого карточка открыта
> why: { ru: "Превращает имя в адрес; без него пользователь знал бы только числа.", en: "..." }
> sequence:                       # диаграмма обмена: рендерит 08/3.1 stepper + пакетоскоп «диаграмма потока»
>   actors: [client, resolver, root, tld, auth]
>   steps:
>     - { from: client, to: resolver, msg: "A? shop.example RD=1", layer: L7 }
>     - { from: resolver, to: root, msg: "A? shop.example", note: { ru: "корень не знает ответа" } }
>     - { from: root, to: resolver, msg: "NS example. + glue" }
>     # ...
> params:                         # ручки объяснения (R4)
>   - { id: ttl, kind: slider, min: 0, max: 86400, default: 300, effect: "второй запрос через t: кэш/полный путь" }
> observe:                        # как увидеть самому
>   - { cmd: "dig +trace shop.example", env: [sim, v86] }
>   - { cmd: "tcpdump -n port 53", env: [sim, v86] }
>   - { capture: C04 }
> breaks:                         # как ломается: симптом → уровень → команда
>   - { symptom: "Could not resolve host", layer: L7, check: "dig @<resolver> name", lab: t6 }
>   - { symptom: "dig висит, ;; connection timed out", layer: L4, check: "nc -vzu <resolver> 53; фильтр UDP/53" }
> docs: [rfc1034, rfc1035, man-dig]
> ```
>
> **Состав каталога.**
>
> | Протокол | Уровень (курса) | Слой | Где ведётся обмен | Как наблюдать | Как ломается (симптом → слой) |
> |---|---|---|---|---|---|
> | DHCP | Н | L7 поверх UDP 67/68, broadcast | DORA | `dhclient -v`, C05 | два сервера → чужой шлюз (L7/L3) |
> | ARP | Н | L2 | who-has / is-at | `ip neigh`, `tcpdump arp` | нет ответа → `Destination Host Unreachable` (L2) |
> | ICMP | Н | L3 | echo, time exceeded, unreachable, frag needed | `ping`, `traceroute`, C02 | фильтр ICMP → PMTU blackhole (L3) |
> | TCP | Н | L4 | SYN/SYN-ACK/ACK, FIN, RST | `ss -tan`, C06–C08 | RST → refused; DROP → timeout (L4) |
> | UDP | Н | L4 | датаграмма без соединения | `ss -uan`, `nc -u` | молчание вместо ошибки; ICMP port unreachable |
> | DNS | Н | L7 | рекурсия + итерации | `dig +trace` | NXDOMAIN, SERVFAIL, старый TTL |
> | HTTP/1.1 | Н | L7 | запрос/ответ | `curl -v` | 4xx/5xx; 502/504 у прокси |
> | HTTPS/TLS 1.3 | Н | TLS | ClientHello…Finished | `openssl s_client`, C09 | срок, имя, цепочка |
> | SSH | Н | L7 поверх TCP 22 | версия → обмен ключами → проверка хоста → аутентификация | `ssh -v`, захват (виден только обмен ключами) | `Host key verification failed`, `Permission denied (publickey)`; опирается на L15 блока Linux |
> | NTP | С | L7 / UDP 123 | запрос/ответ с 4 метками времени | `chronyc tracking`, `timedatectl` | рассинхрон часов → TLS `certificate is not yet valid` (TLS) |
> | SMTP | С | L7 / TCP 25, 587 | EHLO, MAIL FROM, RCPT TO, DATA | `nc mail.lab 25` руками | 25 закрыт у облаков; MX не тот |
> | FTP / SFTP | С | FTP: L7, два соединения; SFTP — подсистема SSH | активный и пассивный режим | захват FTP, `sftp -v` | FTP за NAT без helper ломается — мостик к conntrack helpers |
> | HTTP/2 | С | L7 поверх TLS (ALPN h2) | кадры, потоки, мультиплексирование | `curl --http2 -v`, захват с ключами | head-of-line на TCP; прокси без h2 |

> | WebSocket | С | L7 | `Upgrade: websocket`, 101 | `curl -i -H 'Upgrade: websocket' …`, захват | прокси без `proxy_http_version 1.1` + Upgrade → 400/закрытие |

> | NAT/PAT | С | L3/L4 | трансляция, conntrack | `conntrack -L` | исчерпание портов SNAT; отсутствие обратной трансляции |

> | mTLS | О | TLS | сертификат клиента | `openssl s_client -cert -key` | `certificate required`; мост к service mesh |

> Готовая карточка VXLAN для опытного (она же мост к R9):
>
> **Зачем.** Две машины в разных подсетях должны выглядеть как один L2-сегмент. CNI в Kubernetes (Flannel, Cilium в режиме туннеля) так соединяет поды на разных узлах.
> **Слой.** Кадр Ethernet (L2) едет внутри UDP (L4) внутри IP (L3) — «L2 поверх L4».
> **Обмен.** Обмена нет, VXLAN — чистая инкапсуляция. Схема из конвертов: внутренний кадр (MAC пода, IP пода) → заголовок VXLAN 8 байт (флаги, VNI 24 бита) → UDP dst 4789 → внешний IP узла → внешний Ethernet. Накладные расходы — 50 байт на IPv4. Отсюда MTU пода 1450 при MTU узла 1500.
> **Руками (ярус B, два узла):**
> ```bash
> # node1 (192.168.50.11)
> ip link add vxlan0 type vxlan id 42 dstport 4789 remote 192.168.50.12 dev eth0
> ip addr add 10.244.0.1/24 dev vxlan0 && ip link set vxlan0 up
> # node2 — зеркально, remote 192.168.50.11, адрес 10.244.0.2/24
> ping 10.244.0.2
> tcpdump -ni eth0 udp port 4789     # внешний конверт
> tcpdump -ni vxlan0 icmp            # внутренний
> ```
> **Как ломается.** (1) На `vswitch` включена поломка «drop udp 4789» → ping молчит, оба узла живы. Слой — L4 внешнего конверта. (2) `ping -M do -s 1472 10.244.0.2` не проходит, `-s 1422` проходит. Слой — L3, MTU. (3) Разный VNI → кадры доходят и отбрасываются молча. Слой — L2 оверлея.
> **Проверка.** `when: "net.links[name=vxlan0].vni=42 && probes.icmp['10.244.0.2'].received>=2"`.

> ### N16. Сеть внутри одной машины: netns, veth, bridge (Н базово; С, О полностью; ярус B)
> Вводит: сетевое пространство имён как «отдельный сетевой стек» (`requires: L-ns` из блока Linux), `ip netns`, veth-пару, мост (bridge) как коммутатор внутри ядра, маршрутизацию между пространствами, NAT наружу из пространства, проброс порта внутрь. Понятия 01: `N20`, `N21`.
> Ход урока (каждый шаг — экран с `split` «терминал + схема», схема строится по событиям `ip -j link` из агента v86):
> 1. `ip netns add red`, `ip netns exec red ip a` — внутри только `lo`, и он DOWN. Схема: рамка `net` цвета `--c-ns-net` вокруг пустого стека.
> 2. `ip link add veth-r type veth peer name veth-r-br; ip link set veth-r netns red` — на схеме появляется кабель, один конец внутри рамки. Клик по кабелю: «veth — два интерфейса, кадр, вошедший в один, выходит из другого».
> 3. То же для `blue`. Затем `ip link add br0 type bridge`, оба внешних конца в мост, адреса `10.10.0.2/24` и `10.10.0.3/24` → `ip netns exec red ping 10.10.0.3`. Щуп на `br0` показывает ARP — это коммутатор из N1, только внутри ядра. Команда `bridge fdb show br br0` выводит таблицу MAC.
> 4. Адрес `10.10.0.1/24` на `br0`, default route в пространствах через него, `ip_forward=1`, `iptables -t nat -A POSTROUTING -s 10.10.0.0/24 ! -o br0 -j MASQUERADE` → `ip netns exec red ping <внешний узел>`.
> 5. `iptables -t nat -A PREROUTING -p tcp --dport 8080 -j DNAT --to-destination 10.10.0.2:80` + `nc -l -p 80` в `red` → с соседнего v86-узла `curl http://<node>:8080`.

## 5. BLOCKING — процессных объяснений не хватает, две ссылки ведут в никуда (R3, R4)

**Где:** N5 («интерактив „рукопожатие под лупой“ (раздел 7.3, сцена TCP)»); N10 («интерактивная схема с пятью хуками, см. 7.3, сцена „netfilter“»). В §7.3 таких сцен нет: там описана песочница.

**Что не так.** R3 требует для сетей как минимум: ввод URL (есть, §7.1), разрешение DNS (есть только задачи и `dig +trace`), рукопожатие TCP + TLS (только упоминание), пакет через NAT и роутер (есть в §7.2, экраны 3–4, но без ручек), откуда берётся 504 (есть сценарий T1, объяснения нет). Объяснения DHCP и netfilter тоже нужны: на них ссылается сам документ. R4 требует у каждого объяснения ручки параметров, мгновенный пересчёт с пояснением, «сломай» и перемотку по шагам.

**Исправление: новый §7.10 «Объяснения процессов».** Все объяснения ниже собраны на примитивах 08: `stepper` (3.1), `diagram` (3.2), `packets` (3.6), `breakit` (3.5). Общие правила для каждого:
- полоса шагов внизу с перемоткой ←/→, паузой и скоростью 0,25×/1×/4×;
- каждая стрелка подписана на линии;
- клик по любому элементу открывает карточку «что это / кто создаёт / как посмотреть командой»;
- изменение ручки пересчитывает процесс сразу (свёртка событий заново), а справа появляется строка «что изменилось и почему», с подсветкой изменённых шагов;
- источник шагов — сценарий netlab (детерминированный), опция «проиграть на настоящем v86» там, где это имеет смысл.

> #### E-DNS. Как имя превращается в адрес (N8)
> **Экран 1 — участники.** Слева направо: приложение → stub-резолвер ОС (`/etc/resolv.conf`) → рекурсивный резолвер → корень `.` → TLD `example.` → авторитативный `shop.example`. У каждого блока — подпись роли и адрес.
> **Экран 2 — запрос.** Пошагово идут 8 стрелок. На каждой — реальная строка: `A? shop.example RD=1`; ответ корня `NS a.nic.example. (glue 192.0.2.53)` с подписью «не ответ, а направление»; ответ авторитативного `A 198.51.100.20 TTL 300 AA`.
> **Ручки.** Ползунок «время второго запроса» 0…600 с. При t < TTL путь — 2 стрелки, и у резолвера появляется ярлык «из кэша, осталось 300−t с»; при t ≥ TTL — снова 8 стрелок. Ползунок TTL 30…86400. Переключатель «кэш stub-резолвера ОС (systemd-resolved)» включён или выключен. Переключатель «запись есть в `/etc/hosts`»: путь обрывается на втором блоке, подпись «`dig` этого не увидит, `getent hosts` увидит».
> **Сломай.** «Авторитативный не отвечает» — у резолвера крутится таймер, затем `SERVFAIL`. «Опечатка в TLD» — корень отвечает `NXDOMAIN`, и рядом показано отрицательное кэширование (SOA minimum). «UDP/53 закрыт» — `;; connection timed out; no servers could be reached`.
> **Пересчёт с пояснением (пример).** TTL 300 → 86400: «после смены адреса пользователи этого резолвера будут ходить на старый адрес до 24 часов — это сценарий T5».
> **Проверка.** `predict`: «через 400 с при TTL 300 — сколько стрелок?» (8).
>
> #### E-TCPTLS. Рукопожатие TCP и TLS 1.3 (N5, затем N12)
> **Экран 1 — диаграмма последовательности.** Две вертикальные линии (клиент, сервер), время сверху вниз, расстояние между репликами пропорционально RTT. Стрелки SYN (`seq=x`), SYN-ACK (`seq=y ack=x+1`), ACK. Подписи полей на стрелках. Клик по стрелке открывает пакет в инспекторе.
> **Экран 2 — после N12 добавляется TLS 1.3:** ClientHello (SNI, ALPN, key_share) → ServerHello + {EncryptedExtensions, Certificate, CertificateVerify, Finished} → {Finished} + первый HTTP-запрос. Зашифрованные части нарисованы штриховкой с подписью «видно только концам».
> **Ручки.** RTT 1…300 мс. Справа счётчик: «первый байт ответа через 3×RTT = …». Потери 0…30 %: потерянный SYN перечёркнут, повтор приходит через 1 с, затем 2 с (RTO из модели). Переключатель «TLS 1.2 / 1.3» добавляет или убирает круг. Переключатель «возобновление сессии / 0-RTT» (О): запрос уходит в первом же полёте, с пометкой «повторяемость запроса — риск replay». Переключатель «порт закрыт»: SYN → RST, итог «refused за 1×RTT». Переключатель «межсетевой экран DROP»: SYN, SYN, SYN… с интервалами 1, 2, 4, 8 с, итог «timed out через ~127 с» (моделируемое время с ускорением).
> **Пересчёт с пояснением.** RTT 20 → 150 мс: «сайт из другой части света: та же страница открывается на 390 мс дольше только из-за кругов рукопожатия. Поэтому CDN и keep-alive (E-504, экран 4)».
>
> #### E-WIN. Окно TCP и скорость (N5, С/О)
> Один экран. Отправитель, получатель, «труба» длиной RTT, внутри — сегменты в полёте. Ползунки: окно 4…1024 КБ, RTT 1…200 мс, полоса 10…1000 Мбит/с. Счётчик пропускной способности = min(полоса, окно/RTT). При окне 64 КБ и RTT 100 мс видно, что получается ~5 Мбит/с, и поясняется: «канал простаивает, ждём подтверждений — это bandwidth-delay product». Переключатель «window scaling выключен» фиксирует окно на 64 КБ. Команда для наблюдения: `ss -ti` (rtt, cwnd). Это задание ступени 4 лестницы документации.
>
> #### E-NAT. Пакет через роутер и NAT (N4, N9; расширение §7.2, экраны 3–4)
> К существующим экранам добавить ручки:
> - «Сколько устройств дома» 1…50. Таблица conntrack на схеме растёт, у каждой строки внешний порт.
> - «Внешних IP» 1 или 4.
> - «Таймаут conntrack UDP» 30…180 с. Если ответ DNS приходит позже таймаута, он отбрасывается, и пояснение: «запись уже забыта».
> - «Сломай: исчерпать порты». Ползунок соединений до 65 000 на один внешний IP и один адрес назначения: новые соединения получают отказ. Пояснение: «так выглядит исчерпание SNAT-портов в облачном NAT-шлюзе».
> - Переключатель «без NAT» (маршрутизатор из N4): меняются только MAC и TTL, адреса остаются, и ответ из интернета на `192.168.1.23` не находит дороги — красный ⨯ с подписью.
>
> #### E-NF. Путь пакета через netfilter (N10)
> **Экран — пять хуков.** Блоки PREROUTING → решение о маршруте → INPUT → локальный процесс → OUTPUT → POSTROUTING, плюс ветка FORWARD. В каждом хуке — стопка таблиц (raw, mangle, nat, filter) цветными полосами.
> **Ручки.** Переключатель «пакет к нам / через нас / от нас» перерисовывает путь. Редактор трёх правил: ученик меняет порядок перетаскиванием, и путь пакета пересчитывается — видно, какое правило сработало первым, а счётчик `pkts` растёт ровно на нём. Переключатель «правило `ct state established,related accept` удалить»: ответ на исходящее соединение отбрасывается в INPUT (это T-сценарий «забыто правило established»).
> **Сломай.** Политика FORWARD DROP без разрешения: проброс 8080 из N9 перестаёт работать, подсвечен хук FORWARD.
> **Мост к K8s (О).** Пользовательская цепочка с `-j`-переходами и `-m statistic --mode random --probability 0.5` (замечание 10): пакет идёт то в одну, то в другую ветку. Подпись: «так kube-proxy распределяет запросы по подам — увидите в K4».
>
> #### E-DHCP. Как ноутбук получает адрес (N7)
> Ноутбук без адреса (`0.0.0.0`), Wi-Fi-роутер, широковещательная зона. Шаги DORA с полями на стрелках (`src 0.0.0.0:68 → 255.255.255.255:67`, `yiaddr`, опции 1, 3, 6, 51). Ручка «время аренды» 60 с…24 ч: на полосе времени появляются renew на 50 % (T1) и rebind на 87,5 % (T2). Сломай: «второй DHCP-сервер» — два Offer, и клиент берёт первый; «сервер выключен» — Discover повторяется, затем адрес `169.254.x.x` с подписью «link-local: сервера не нашли».
>
> #### E-504. Откуда берётся 504 (N13, N15)
> **Экран 1 — цепочка.** Клиент → балансировщик (L7, idle timeout) → nginx (`proxy_connect_timeout`, `proxy_read_timeout`) → приложение (свой таймаут к базе) → база. Под каждым блоком — его таймер в виде шкалы.
> **Ручки.** «Время ответа базы» 0…120 с. «`proxy_read_timeout`» 5…300 с, по умолчанию 60 с. «Таймаут приложения к базе» 5…60 с. «Idle timeout балансировщика» 30…600 с. Переключатель «`proxy_next_upstream` на второй бэкенд».
> **Пересчёт.** Процесс проигрывается заново, и первым срабатывает самый короткий таймер на пути. На этом блоке загорается ярлык «ответ создал я» — это главный смысл объяснения: код ответа говорит, **кто** его написал.
> - База 75 с, `proxy_read_timeout` 60 с → «504 сгенерировал nginx; в `error.log` — `upstream timed out … while reading response header`».
> - Таймаут приложения 30 с → «приложение само вернуло 500 через 30 с; nginx честно передал 500 дальше».
> - Idle timeout балансировщика 45 с → «504 от балансировщика, в логах nginx запроса нет».
> **Сломай.** «Приложение не запущено» → мгновенный RST → 502 `connect() failed (111…)`. «Межсетевой экран между nginx и приложением DROP» → 504 через `proxy_connect_timeout` с текстом `while connecting to upstream` (сценарий T2). «Приложение возвращает мусор» → 502 `upstream sent invalid header`.
> **Линзы 08/3.11** (Dev / Ops / пользователь / пустая «мониторинг») — на последнем шаге.
> **Проверка.** `hotspot`: «кто написал этот 504?» по выводу `curl -sv` (заголовок `Server:`) и строке лога.

Отдельно. §6, абзац «Из движка Sankofa берём» дополнить строкой: «процессные объяснения блока — §7.10; каждое регистрируется в `content/net/explainers/*.steps.yaml` в формате 08 §7.6».

## 18. MINOR — QR-передача: снимок колоды повторений не помещается в 213 байт

**Где:** §6, пункт про `engine/qr.ts` («QR несёт ссылку с состоянием колоды повторений»).

**Что не так.** Кодер Sankofa ограничен версией 10 и 213 байтами (08 §3.9). Состояние колоды FSRS даже на 50 карточек (стабильность, сложность, дата на каждую) после сжатия не влезет.

**Исправление.** QR несёт только урок, режим (`drill=D1..D9`), зерно генератора и уровень сложности. Колода на телефоне начинается заново или синхронизируется через аккаунт (09 §3.4). Офлайн-перенос колоды — файлом экспорта (09 §3.3).

## 22. MINOR — `mtr` «не поддерживается»

**Где:** §7.3.3, последняя строка.

`mtr` — стандартный инструмент дежурного, и он удобнее связки `traceroute` + `ping` для задачи «где теряются пакеты». В netlab его вывод — просто агрегат уже смоделированных ICMP. Предлагаю поддержать `mtr -n -r -c N` (отчётный режим, без интерактива). Это даёт задание ступени 3: «найдите режим отчёта без интерактивного экрана» (`-r`/`--report`).
