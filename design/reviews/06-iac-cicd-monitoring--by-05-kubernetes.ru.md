# Рецензия на 06-iac-cicd-monitoring.md (рецензент: роль Kubernetes, автор 05-kubernetes.md)

Дата: 18.11.2026. Прочитан документ 06 целиком; для сверки — 01 (граф понятий, порядок блоков, проверки уровня), 05 (kube-lite, Helm, реальный этап), 07 (методология, DORA), 08 (примитивы и визуальный язык), 09 (ярусы, контракт проверок, агент `trainer-check`, сеть v86).

## Вердикт

Документ сильный в инженерной части: симуляторы (ansim, tfsim на настоящем HCL, свой PromQL с прогоном `promqltest`), «эталонные стенды» в CI, `promql_equiv` на нескольких наборах данных, инцидент C13 с доказательствами через запросы — это лучшее, что есть в комплекте документов по проверяемости. Но в нынешнем виде его нельзя отдавать в разработку по трём причинам. **Первая:** он расходится с общим каркасом: другой порядок блоков (Git и YAML до сетей, хотя в 01 CI/CD с Git идёт после Docker, а C04 требует N14), свои строковые идентификаторы понятий вместо графа 01, свой контракт проверок вместо `goals`/фактов из 09, свой проверяльщик практикума вместо агента `trainer-check`, свои проверки уровня, которые не совпадают с 01 §4.3, и модуль A0, который дублирует блок методологии 07 (там пять метрик DORA, здесь четыре). **Вторая:** требования владельца второй волны почти не покрыты. Лестницы документации (R2) нет совсем. Объяснения процессов (R3) есть только как сцены прокрутки без параметров и без «сломай» (R4), а местами в них прямо запрещённое: тушь, «человечек», сюжет «пятничного релиза», бот «Петя». Этап 3 Kubernetes с Terraform и Ansible (R12) противоречит порядку блоков. Мост «цикл сверки ↔ IaC ↔ GitOps» (R10) не построен. **Третья:** стык с Kubernetes (A7, C16) недоопределён. Деплой в кластер из CI сделан «моделью инструмента» мимо kube-lite и `helm-engine.wasm`, метрики кластера не связаны с состоянием kube-lite. Ниже 30 замечаний; к каждому блокирующему и большинству серьёзных приложен готовый текст, который можно вставить.

### 1. BLOCKING — Порядок блоков Git/YAML противоречит 01 и графу понятий

### 3. BLOCKING — Свой контракт проверок вместо «фактов → предикатов» из 09
**Где:** 0.4 (таблица типов проверок, пример `a3-d1`), 7 (проверяльщик практикума).

**Что не так.** 09 §2.4 уже свёл типы проверок 06 к форме `goals[]` с `when`/`keep`/`fail`/`envs`, а вычислители `yaml_path`, `lint`, `plan_expect`, `promql_equiv` оставил как подключаемые, но с общим результатом `CheckResult`. В 06 остался старый формат `checks:`. Обратная связь там описана как `forbid.message`, а не `fail[].say` + `fail[].term`. Поле `term` обязательно: по нему ученика отправляют к уроку, где термин введён, и это требование самого 06 (0.4, «какой термин повторить»).

**Исправление — `a3-d1` в формате 09 (вставить вместо примера в 0.4):**

```yaml
id: a3-d1
kind: pipeline-fix
level: L0
doc_step: 2                          # ступень лестницы документации, см. №4
task:
  ru: "Джоба deploy падает с «dist/: No such file or directory». Сделайте так, чтобы результат сборки дошёл до деплоя."
  en: "The deploy job fails with 'dist/: No such file or directory'. Make the build result reach the deploy job."
start: { repo: fixtures/site-no-artifacts, pipeline_file: .gitlab-ci.yml }
goals:
  - id: g-lint

  - id: g-run

    fail:
      - if: "pipeline.last.jobs[name=deploy].log~'dist/: No such file'"
        say: { ru: "deploy всё ещё не видит dist/: у build нет artifacts:paths", en: "deploy still cannot see dist/: build has no artifacts:paths" }
        term: C09
  - id: g-artifact
    eval: { yaml_path: "$.build.artifacts.paths", contains: "dist/" }
  - id: g-no-rebuild
    eval: { yaml_path: "$.deploy.script[*]", not_matches: "npm (ci|install|run build)" }
    fail:
      - say: { ru: "Деплой не должен собирать сайт заново: сборка — работа джобы build.", en: "Deploy must not rebuild the site." }
```

Симулятор пайплайнов должен отдавать факты в схеме `dt.facts/v1` с областью `pipeline` (`pipelines[].jobs[].{name,status,log,artifacts,startedAt,finishedAt,runner}`). Такие же области нужны ansim (`ansible.runs[].hosts[].tasks[]`), tfsim (`tf.state`, `tf.plan`) и мониторингу (`prom.targets`, `prom.rules`, `am.routes`). Эти области надо добавить в 09 §2.2, а в 06 — сослаться на них.

**Практикум (раздел 7).** `docker run ghcr.io/<org>/devops-trainer-checker` заменить агентом `trainer-check` из 09 §5.4 с треком `iac-pet`: `trainer-check run --track iac-pet --nonce …`. Области фактов для трека: `prom.targets` (`/api/v1/targets`), `prom.rules`, `grafana.dashboards` (по UID), `http` (проба приложения), `tf.state` (агент читает файл с выводом `terraform show -json`, который ученик кладёт рядом), `ansible.rerun` (вывод второго прогона).

### 4. BLOCKING — Нет лестницы документации (R2)
**Где:** отсутствует во всех блоках G, A, B1, B2, C.

**Что не так.** Нигде не сказано, как ученик учится читать `man git-*`, справочник GitLab CI, `ansible-doc`, страницы провайдеров Terraform и справочник функций PromQL. **Анатомия страниц, которой учим на ступени 2** (подсветка раздела во фрагменте):

1. Облако хранит ресурсы и знает о них всё, но не знает, что они «ваши».
2. Код описывает, какими ресурсы должны быть, но не знает, какие есть.
3. State — файл, где Terraform записал связь «адрес в коде ↔ ID в облаке» и последние известные атрибуты.
4. `plan` сначала обновляет state по облаку (refresh), затем сравнивает код со state.
5. Отсюда три вида расхождения: нет в state (`+`), есть, но иначе (`~` или `-/+`), есть в state, нет в коде (`-`).
6. Потеря state не трогает облако, но отнимает у Terraform память; поэтому state хранят удалённо и блокируют.
7. В state лежат значения атрибутов, включая секреты, — это файл с доступом как к паролям.
