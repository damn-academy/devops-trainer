Дата: 18.11.2026. Документ под рецензией не редактировался.

## Вердикт

Документ сильный: последовательный принцип «квиз учит, экзамен измеряет», каталог заблуждений как основа дистракторов, проверка по состоянию, честная позиция по ИИ и проверка цитат в оценке нейросетью сделаны хорошо, и их надо сохранить. Карьерный блок по шагам 8–11 чек-листа доведён до тренажёров, а не до советов. В текущем виде документ всё же нельзя отдавать в разработку. Требования владельца второй волны в нём не отражены: лестница документации R2 не встроена в оценивание и прямо конфликтует с правилом «задание только по введённым понятиям», процессные объяснения R3/R4 не стали предметом проверки, изоляция в Linux (R6), шесть границ контейнера (R7), каталог протоколов (R8), сеть Kubernetes (R9), цикл согласования (R10), гибридный кластер (R11) и три этапа Kubernetes (R12) в банке и экзаменах не появляются. Кроме того, документ объявляет «единый формат экзамена», которому не соответствуют экзамены в `03`, `04` и `05`. С `09` он расходится в устройстве подписи и серверной части, с `01` — в весе объяснений на экзамене и в расписании карьерного блока. Квизы нарушают порядок понятий: в квизе методологии встречаются образ, registry, GitOps и IaC. Найдено и несколько фактических ошибок: группировка метрик DORA, «образ с другим ядром», `journalctl -u nginx` как журнал nginx. Ниже 36 замечаний: 10 BLOCKING, 16 MAJOR, 10 MINOR. Почти к каждому приложен готовый текст.

### 2. BLOCKING — Процессные объяснения (R3/R4) не являются предметом проверки

**Где:** раздел 2 (типы заданий), 4 (квизы), 8 (образцы).

**Что не так.** R1 называет объяснения процессов одним из трёх оснований курса, R3 требует их в каждом блоке. Оценивание же знает о схемах только через `hotspot` и `label`, то есть через *статичную* картинку. В нём нет заданий, которые используют главное свойство объяснений — ползунок, переключатель, «сломай», прокрутку шагов. Ученик может пройти объяснение глазами и ни разу не предсказать, что изменится при смене параметра. Такое знание пассивно, и оно не проверяется.

**Исправление — новый тип и правило покрытия.**

| Тип | Что проверяет | Как проверяется |
|---|---|---|
| `scene` (новый, на `stepper` + `diagram` + `breakit` из `08`, 3.1–3.5) | Модель процесса: предсказать следующий шаг, эффект параметра, симптом поломки | Задание ставит сцену в начальное состояние (`scene: <id>`, `set: {param: value}`, `step: n`) и задаёт подвид: `next` — какой узел или стрелка загорится следующей (`hotspot` по `node.id`); `param` — ученик двигает ползунок до значения, при котором наступит условие (проверка по состоянию сцены); `break` — компонент удалён, ученик выбирает симптом или кликает место первой ошибки; `scrub` — ученик прокручивает шаги и останавливается на шаге, где возникает названное событие |

Правило для линтера: у каждого процессного объяснения из списка R3 есть ≥ 2 задания `scene` разных подвидов, и хотя бы одно попадает в квиз блока. Без этого блок не собирается.

Пример записи:

```yaml
id: net.dns-resolution.s03
kind: scene
scene: net.dns-resolution          # объяснение «как резолвится имя» (03)
subkind: param
level: [L0, L1, L2]
concepts: [N08, N09]
set: { cache: warm, ttl_s: 300 }
q:
  ru: "Администратор сменил A-запись shop.example в 12:00. Передвиньте ползунок «время запроса» на первый момент, когда резолвер провайдера гарантированно отдаст новый адрес."
answer: { when: "scene.t >= scene.cached_at + ttl_s" }   # 12:00 + остаток TTL кэша, вычисляет сцена
options_why:
  early: { misconception: net.dns-change-instant, ru: "Резолвер отдаёт копию из кэша, пока не истёк TTL; смена записи на авторитативном сервере не видна сразу." }
```

Минимальный набор заданий `scene` по объяснениям R3 (подвид — что проверяется):

| Блок | Объяснение | Задания |
|---|---|---|
| Методология | Задача от идеи до прода; узкое место потока | `param`: поднимите WIP колонки «Ревью» до значения, при котором lead time перестаёт падать; `break`: уберите автотесты — где первым вырастет очередь |
| Методология | Инцидент: алерт → постмортем | `scrub`: остановитесь на шаге, где сервис уже восстановлен, а причина ещё не найдена (mitigation ≠ fix) |
| Linux | Загрузка; fork/exec/PATH; pipe; systemd перезапускает службу | `next` после `fork()`; `param`: `Restart=on-failure`, `StartLimitBurst=3` — на каком падении systemd перестанет перезапускать; `break`: убрать каталог из PATH — какой шаг упадёт |
| Сети | URL; DNS; TCP+TLS; пакет через NAT; откуда 504 | `next` в рукопожатии; `param`: `proxy_read_timeout` против времени ответа — при каком значении 504 сменится на 200; `break`: межсетевой экран отбрасывает SYN — клиент видит 504 или 502 |
| Контейнеры | `docker run` CLI → процесс; `docker build` по слоям с кэшем; pull по манифесту | `scrub` до шага, где появляется PID процесса; `param`: какую строку Dockerfile изменить, чтобы пересобрались ровно 2 слоя; `break`: registry вернул 404 на манифест для платформы — где ошибка |
| Kubernetes | `kubectl apply` через компоненты; планирование; rolling update; отказ узла; запрос через Service/Ingress | `param`: `maxUnavailable`/`maxSurge` — сколько подов будет одновременно при 4 репликах; `break`: kubelet на узле остановлен — через сколько секунд поды пересоздадутся (по toleration `not-ready` 300 с); `next` для пакета на ClusterIP |
| CI/CD | `git push` → выкладка | `break`: токен registry истёк — какая джоба красная, что увидит прод |

| Мониторинг | scrape → TSDB → PromQL → алерт → уведомление | `param`: `scrape_interval` и окно `rate()` — при каком окне график станет пустым (окно < 2 интервалов); `param`: `for: 5m` — алерт pending или firing после 3-минутного всплеска |

### 3. BLOCKING — Изоляция в ядре (R6) отсутствует в квизе Linux и в экзамене Linux

**Где:** 8.2, 6.2 (Linux-экзамена нет), 9.2 (обязательные вопросы, строка Linux).

**Что не так.** Все пять заданий Linux проверяют только классический минимум. По R6 namespaces, cgroups v2, capabilities, overlayfs и потоки вводятся в Linux. Сейчас D-2 и K-4 опираются на D03/D04 как на понятия Docker-блока, а тренажёр «контейнер vs ВМ» ссылается на `unshare` из урока контейнеров. В графе `01` (моя зона) понятия D03–D05 и capability переедут в Linux. В `10` нужно поменять ссылки и добавить задания.

**Исправление — добавить в 8.2 (новые ID условные, до обновления графа: L33 поток, L34 namespaces, L35 cgroups v2, L36 capabilities, L37 overlayfs, L38 seccomp-идея):**

**L-6. `predict`, L1–L2, понятия L17, L33.** У процесса `java` PID 812. Что выведет `ls /proc/812/task | wc -l`, если `ps -o nlwp= -p 812` показывает `37`?
- **а) `37` — верно: каталог `task` содержит по подкаталогу на каждый поток (TID); `nlwp` — их число.**
- б) `1` — *неверно: один — только у однопоточного процесса; у потоков общий PID (TGID), но свои TID.*
- в) Ошибку: у потоков нет записей в `/proc` — *неверно: потоки видны в `/proc/<pid>/task/` и в `ps -eLf`.*
- г) Число дочерних процессов — *неверно: дочерние процессы — отдельные PID с собственными каталогами `/proc/<pid>`.*

**L-7. `task`, L0–L2, понятия L35, L18.** «Процесс `hog` съедает память. Ограничьте его 32 МБ, не перезапуская, и убедитесь, что при превышении ядро его убьёт.» Среда v86 (`lab-debian`).
Проверка (предикаты `09`, 2.3): `cgroups[procs~@pid(hog)].memory.max<=32M` до срабатывания; затем `cgroups[path~@cg(hog)].memory.events.oom_kill>=1 && !procs[cmd=hog]`. `fail`: `memory.max=max` — «группа создана, лимит не записан»; процесс в корневой группе — «PID не перенесён в `cgroup.procs`». Разбор: строка `oom-kill` в `dmesg` и `memory.events`. Это тот же механизм, что `OOMKilled` в K-4, и разбор K-4 должен ссылаться на это задание.

**L-8. `choice`, L1–L2, понятие L34.** Вы запустили `unshare --pid --fork --mount-proc bash` и внутри выполнили `ps -ef`. Что увидите?

## C. Фактические и технические ошибки

### 21. MAJOR — M-4: метрики DORA сгруппированы неверно

**Где:** 8.1, M-4, вариант б.

По текущему руководству DORA ([dora.dev/guides/dora-metrics](https://dora.dev/guides/dora-metrics/), обновлено 05.01.2026) метрики делятся на **throughput**: change lead time, deployment frequency, **failed deployment recovery time** — и **instability**: change fail rate, deployment rework rate. В документе время восстановления отнесено к стабильности, а rework rate описан как «с 2025 года ещё доля незапланированных выкладок, rework rate», будто это две метрики. Это одна метрика: доля выкладок, которые были незапланированными и чинили видимый пользователям дефект. В отчётах DORA она появилась в 2024 году, а не в 2025-м.

Готовый текст варианта б: «**Скорость выросла, стабильность упала; итоговое улучшение не доказано — верно: DORA смотрит на две группы вместе: пропускную способность (время от коммита до прода, частота выкладок, время восстановления после неудачной выкладки) и нестабильность (доля неудачных изменений и доля незапланированных выкладок-исправлений, rework rate).**»

### 22. MAJOR — D-2: «образ с другим ядром» — само по себе заблуждение

**Где:** 8.4, D-2, вариант а.

В образе контейнера нет ядра. Фраза «образ с другим ядром (например, Windows на Linux-хосте) без ВМ не запустить» закрепляет у новичка ровно то заблуждение, которое должна разрушать (`docker.image-contains-kernel`). Исправление: «…поэтому контейнер стартует за доли секунды, а программу, которой нужно другое ядро (например, Windows-приложение на Linux-хосте), в контейнере без ВМ не запустить: в образе нет ядра, есть только файлы». Добавить заблуждение в каталог и сделать его дистрактором в D-2 (вариант «Свой лёгкий экземпляр ядра»).

### 23. MAJOR — L-3: `journalctl -u nginx` не показывает журнал nginx

**Где:** 8.2, L-3.

nginx по умолчанию пишет `error.log` и `access.log` в `/var/log/nginx/`, а в журнал systemd попадают только сообщения запуска и остановки на stderr. Ответ «журнал службы nginx за последний час = `journalctl -u nginx --since "1 hour ago"`» верен формально для unit, но на практике вводит в заблуждение. Это же заблуждение потом ломает дрилл «504»: там ученик должен читать `error.log`. Исправление: заменить службу на ту, что пишет в journald (`ssh` / `sshd` или учебная служба `shop-api`), и добавить в разбор строку: «у nginx свои файлы журналов — `/var/log/nginx/error.log`; `journalctl -u nginx` покажет только запуск и остановку». Либо сделать из этого отдельное задание `choice` «где искать причину 502 у nginx».

### 24. MINOR — L-2 и N-5: понятия вне графа

L-2 опирается на «файловый дескриптор» и `lsof`. В графе нет ни понятия дескриптора, ни `lsof`: в `02` `lsof +L1` есть в модуле L13, но в графе `01` нет соответствующего понятия. В квизе Linux встречается nginx (N19 — блок Сетей). N-5 опирается на `tcpdump` и `mtr`, которых в графе нет. Исправление: в L-2 заменить nginx на «служба `report`», в `concepts` добавить новое понятие «файловый дескриптор, `/proc/<pid>/fd`, `lsof`» (добавлю в граф как L39, требует L26). В N-5 указать понятие «захват пакетов, `tcpdump`» (добавлю как N23, требует N07) или убрать строку.

### 25. MINOR — K-1: список понятий неполон; K-2 опирается на DNS кластера

K-1 проверяет Deployment, ReplicaSet и controller-manager: в `concepts` должны быть K11, K12, K27, а не только «K02–K08, K11». K-2 использует `curl http://web`, то есть K16 (CoreDNS), которого нет в списке. Без этого правило «задание показывается, когда все понятия introduced» не сработает.

### 26. MINOR — I-5, вариант б: «план изменений до применения не показывается»

У Ansible есть `--check --diff`, предварительный просмотр изменений внутри ВМ. Разбор неточен. Готовый текст: «*неверно как лучший ответ: модули есть, но Ansible не хранит state ресурсов облака: удалить ВМ, исчезнувшую из плейбука, он не догадается, и надёжного плана изменений облака, как `terraform plan`, у него нет (`--check` для облачных модулей поддерживается не везде).*»

### 27. MINOR — C-1: `forbid` использован как «засчитывается с пометкой»

`forbid` по `06` и `09` означает «не засчитывается». Для `only/except` нужен отдельный механизм — `warn`: «засчитывается, разбор с пометкой». Предлагаю добавить в формат: `warn: { when: "yaml_path(.deploy.only)", say: {...} }`.

### 28. MINOR — D-3: гонка в условии

`docker exec db psql …` сразу после `docker run -d postgres:16` часто падает: база ещё инициализируется (`the database system is starting up` или нет сокета). Это `predict`, и эталон генерирует симулятор. Если `dsim` моделирует время инициализации, вывод разойдётся с вопросом. Добавить в условие строку «(дождавшись, пока база будет готова)» или шаг `until pg_isready`. Отдельно: с postgres 18 каталог `VOLUME` сменился на `/var/lib/postgresql`. Вариант параметризации с версией 18 должен менять и путь в разборе.

### 29. MINOR — Голос: `SpeechRecognition.available()` вызывается без `quality`; whisper-base плох для русского

**Где:** 9.3.

По MDN ([SpeechRecognition.available()](https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition/available_static)) у опций есть `quality` (`command` по умолчанию, `dictation`, `conversation`), а результат бывает `available`, `downloadable`, `downloading`, `unavailable`. Для интервью нужен `quality: "conversation"` или хотя бы `"dictation"`. При `downloadable` следует предложить `SpeechRecognition.install(...)`, а не сразу уходить на сервер. `whisper-base` на русском даёт заметно больше ошибок, чем на английском. Слова-паразиты и проверка дословных цитат (`evidence` должна «дословно встречаться в расшифровке») чувствительны к ошибкам распознавания. Предложение: для RU по умолчанию `whisper-small` (WebGPU) с запасным `base`, а проверку цитат делать нечёткой (нормализованное расстояние Левенштейна ≤ 0,15 по словам). Иначе честные баллы будут сбрасываться из-за ошибок распознавания.

### 30. MINOR — Зарплатные данные устарели к моменту выпуска

**Где:** 9.8. «По вакансиям августа 2025 года» в документе от 18.11.2026 — данные 15-месячной давности. Правило «карточка без даты не попадает в сборку» есть, правила свежести нет. Добавить в линтер: «рыночные цифры старше 6 месяцев на дату сборки — предупреждение, старше 12 — ошибка».

### 34. MAJOR — Один и тот же банк для L0 и L2: опытный решает задания новичка
