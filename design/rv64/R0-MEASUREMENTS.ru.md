# Трек RV64, этап R0: замер TinyEMU в браузере

Состояние на 21.11.2026: замер проведён. Контекст решения описан в `00-DESIGN.ru.md`, раздел 6.12: мы пишем собственный движок RV64GC с MMU Sv39 и JIT-компиляцией в WebAssembly, проходим этапы R0–R4, а операционной системой узла будет kuberoot для riscv64, а не k3s.

## Коротко о результате

TinyEMU, интерпретатор RV64 Фабриса Беллара, скомпилированный в WebAssembly, загружает Linux для riscv64 во вкладке Chromium меньше чем за секунду и выполняет настоящие программы из Alpine для riscv64: kubectl 1.36, etcd 3.6 и kube-apiserver 1.36. На Apple M4 он выполняет около 250 миллионов полезных гостевых инструкций в секунду. Это примерно шестая часть ядра SiFive U74, на котором построена плата VisionFive 2, и шестидесятая часть ядра самого ноутбука. С такой скоростью команда `kubectl get pods`, обращённая к локальному apiserver, выполняется 1,6–1,9 с, то есть превышает бюджет в 0,5 с **в 3,3–3,8 раза**. Холодный запуск управляющего слоя занимает 75 с, поэтому бюджет в 5 с на запуск узла **одной скоростью процессора не достигается вовсе, и для него нужны снимки**. Кроме того, замер выявил три недостатка, которых R1 должен избежать с самого начала. В сборке 2019 года нет регистра `time`, и каждая программа на Go завершается сигналом SIGILL. Цикл эмулятора в главном потоке тратит 30–40 % времени на то, чтобы уступать управление браузеру через `setTimeout`. Наконец, в его ядре Linux 4.15 нет overlayfs, и среда исполнения контейнеров на нём работать не может.

## Как проводился замер

- **Машина.** Apple M4 с десятью ядрами и 16 ГБ памяти под macOS, Chromium 159.0.8154.6 из Playwright без окна. Одновременно работал только один браузер, страницу отдавал сервер разработки Vite с заголовками COOP и COEP, так что вкладка была изолирована от других источников. Виртуальные машины и контейнеры не использовались.
- **Варианты эмулятора.**
  - `r0` — TinyEMU версии 2019-12-21, пересобранный Emscripten 6.0.9 с оптимизацией `-O3` скриптом `build-tinyemu.sh`. В сборку внесены две правки: счётчики выполненных инструкций и времени, проведённого в интерпретаторе (по ним считается скорость в миллионах инструкций в секунду), и регистр `time`, о котором рассказано в разделе «Что обнаружилось».
  - `r0slice` — та же сборка, но за один проход цикла в главном потоке она выполняет 30 миллионов гостевых инструкций вместо 3 миллионов. Этот вариант показывает, сколько выиграл бы цикл, который вовсе не уступает управление.
  - `bellard` — готовая сборка `riscvemu64-wasm` из официального пакета JSLinux 2019-12-21 без изменений.
- **Гость.** Загрузчик bbl и ядро Linux 4.15 из того же пакета JSLinux, один процессор, 1024 МБ памяти и корневой диск ext4 на 400 МБ, который подгружается по HTTP блоками по 256 КиБ по мере обращения к ним. На диске лежат minirootfs Alpine 3.24.4 для riscv64, программы `kubectl`, `kube-apiserver` и `etcd` из репозитория community того же Alpine, наши статически собранные тесты на Go и CoreMark. Вторым, минимальным гостем служит образ с busybox из пакета JSLinux на 128 МБ.
- **Как измерялось время.** Все числа — время по часам хоста. Страница засекает момент, когда команда набрана в консоли, и момент, когда в консоли появилась метка её завершения. Время внутри гостя, то есть `/proc/uptime` и собственные часы CoreMark, в браузерной сборке TinyEMU идёт по часам хоста и совпадает с этими измерениями.
- **Источники.** Каждый скачанный файл описан в `web/src/engine/rv64-r0/manifest.json` с адресом, версией, контрольной суммой SHA-256 и лицензией. Исходные результаты в формате JSON лежат в `web/public/rv64-r0/results/` и в репозиторий не попадают.

### Память вкладки

Когда гостю выделено 1024 МБ, куча WebAssembly занимает 1032 МБ адресного пространства, но браузер выделяет физическую память только под те страницы, которых гость уже коснулся. Поэтому пиковая резидентная память процесса отрисовки вкладки составила 230–490 МБ в разных прогонах и 300–380 МБ в прогонах с управляющим слоем. Функция `performance.measureUserAgentSpecificMemory()` в Chromium без окна ничего не вернула, так что эти числа взяты у операционной системы: это резидентная память процесса отрисовки по данным `ps`.

## Что обнаружилось

1. **В TinyEMU 2019 года нет регистра `time`.** Среда исполнения Go читает таймер инструкцией `rdtime` в пользовательском режиме, а TinyEMU отвечает на неё исключением «недопустимая инструкция». Поэтому каждая программа на Go, включая kubectl, сразу при запуске завершается сигналом SIGILL, и неизменённая сборка JSLinux ведёт себя так же. Наша сборка возвращает в этом регистре значение машинного таймера и открывает бит TM в `mcounteren`, и после этой правки kubectl, etcd и kube-apiserver работают.
2. **Уступание управления браузеру отнимает 30–40 % времени.** Эмулятор работает в главном потоке отрезками по 3 миллиона инструкций и после каждого отрезка возвращается в цикл событий через `setTimeout(0)`, а браузер ограничивает такие вложенные таймеры минимумом в 4 мс. Пока шёл CoreMark, интерпретатор работал только 59–70 % времени. С отрезками по 30 миллионов инструкций эта доля выросла до 94 %, CoreMark ускорился примерно в полтора раза, а время отклика консоли не изменилось. Поэтому движок R1 работает в отдельном Web Worker и управление не уступает никогда.
3. **Ядро и прошивка TinyEMU для Kubernetes не годятся.** Ядро из комплекта TinyEMU — это Linux 4.15 без overlayfs, а сам TinyEMU реализует привилегированную архитектуру версии 1.10 вместе с интерфейсом SBI 0.1 из загрузчика bbl. Среда исполнения контейнеров на таком ядре работать не может, а современному ядру вроде ядра kuberoot нужен SBI версии 0.2 или новее. Загрузить современное ядро на TinyEMU мы не пытались, потому что в R1 прошивку всё равно заменит SBI, реализованный в самом движке.
4. **Мелочи настройки гостя, которые унаследует R1.** У гостя нет часов реального времени, поэтому страница передаёт время хоста в командной строке ядра. etcd отказывается запускаться на riscv64, пока не задана переменная `ETCD_UNSUPPORTED_ARCH=riscv64`. Интерфейс обратной петли должен включать скрипт инициализации.
5. **Холодный запуск больших программ обходится дорого.** Первый вызов `kubectl` длится в 2,6–3 раза дольше второго, потому что 65 МБ дисковых блоков приходят по одному блоку в 256 КиБ. В настоящей сети это будет медленнее, чем с локального сервера разработки, поэтому снимки должны включать кэш страниц тех программ, которые вызывает курс, а ленивый диск должен заранее подкачивать блоки часто используемых файлов.

| `curl` к Service не дольше 0,3 с | Путь команды до оболочки гостя и обратно — 35 мс | выдержан | Путь по сети через `dt-switch` пока не измерен |

**Вывод.** Движок должен быть примерно **в четыре раза быстрее TinyEMU по полезной скорости гостя**, то есть выполнять около 1000 миллионов полезных инструкций в секунду на ноутбуке класса M4, а запуск узла без снимков не уложится в бюджет ни при какой скорости. Работа в Web Worker без уступания управления даёт примерно полтора раза из этих четырёх. Остальное должен дать JIT, причём с запасом: на настоящем узле будут работать более тяжёлое современное ядро, kubelet и containerd, а два узла поделят между собой один ноутбук. Поэтому цель R2 — ускорение не меньше чем в три раза относительно интерпретатора уровня TinyEMU, работающего без уступания управления.

## План этапов R1–R4

### R1. Интерпретатор на Rust, скомпилированный в WebAssembly

**Решение: интерпретатор пишется на Rust и собирается под `wasm32-unknown-unknown`, а вокруг него остаётся тонкий слой на TypeScript.** Доводы приведены в порядке их веса.

1. **Шестьдесят четыре бита без накладных расходов.** Каждый регистр RV64 хранит 64-битное целое число. Rust переводит арифметику над `u64` прямо в инструкции `i64` языка WebAssembly. Код на TypeScript после `tsc` исполняется как JavaScript, а там 64-битное целое — это либо `BigInt`, который выделяет память на каждую операцию и работает в десятки раз медленнее, либо пара 32-битных чисел, и тогда на одну гостевую инструкцию приходится от двух до четырёх операций с ручным переносом разрядов. AssemblyScript дал бы тип `i64`, но его инструменты, отладка и библиотеки заметно беднее, а JIT на этапе R2 потребует надёжного кодировщика модулей WebAssembly.
2. **Тот же код запускается на машине разработчика.** Команда `cargo test` прогоняет riscv-tests, сигнатуры riscv-arch-test и сравнение трасс с эталонным эмулятором без браузера, на ноутбуке и в CI; сборка для браузера собирается из того же крейта.
3. **Общая память и потоки для R3.** Rust собирает WebAssembly с возможностями `+atomics,+bulk-memory` и импортирует общую `WebAssembly.Memory`, а это и есть устройство R3: одна оперативная память гостя в `SharedArrayBuffer` и по одному процессорному ядру гостя в каждом Web Worker.
4. **Для JIT нужен кодировщик WebAssembly.** Библиотека `wasm-encoder` от Bytecode Alliance (лицензия Apache-2.0 с исключением LLVM) собирает модули прямо в процессе работы, поэтому транслятор остаётся обычным кодом на Rust.
5. **Безопасность памяти в большом декодере и MMU.** В C ошибка на единицу в таблице страниц тихо портит память гостя, и её ищут неделями; Rust ловит такие ошибки при компиляции или проверкой границ.

Язык C, на котором написан TinyEMU, был бы так же быстр, но мы лишились бы второго и пятого доводов, а корректность JIT стало бы труднее поддерживать. На TypeScript остаются интерфейс `Machine` с новым видом `kind: 'rv64'` (раздел 6.2 дизайна), терминал, мост к коммутатору `dt-switch`, загрузчик снимков и схемы курса.

**Что делает интерпретатор R1.**

- **Набор инструкций.** RV64IMAFDC с Zicsr и Zifencei, а с первого дня ещё и те расширения, которые стоят недорого и важность которых показал замер. Первое из них — Zicntr с настоящим регистром `time`: в TinyEMU 2019 года этого регистра нет, и каждая программа на Go завершалась сигналом SIGILL на инструкции `rdtime`, пока мы не добавили регистр в нашу сборку. Второе — Sstc с регистром `stimecmp`, благодаря которому таймер ядра не ходит через машинный режим на каждом тике. Третье — Zba, Zbb и Zbs из базового профиля RVA22: программы на Go, собранные с `GORISCV64=rva22u64`, выполняют с ними меньше инструкций. Привилегированная архитектура версии 1.12, трансляция адресов Sv39; Sv48 добавим, если её попросит kuberoot.
- **Без загрузки прошивки.** Интерфейс SBI версии 2.0 реализует сам эмулятор: расширения TIME, IPI, RFENCE, HSM, SRST, DBCN и старую консоль. Поэтому стадии bbl или OpenSBI при загрузке нет, а в машинный режим процессор попадает только ради того немногого, что требуется SBI. Ядро загружается вместе с деревом устройств, которое строит движок.
- **Устройства.** CLINT с машинным таймером по часам хоста, контроллер прерываний PLIC и устройства virtio-mmio 1.x: диск с ленивой загрузкой блоков по HTTP, как в TinyEMU, и кэшем в Cache Storage, сетевая карта, кадры которой уходят в `dt-switch`, консоль, файловая система 9p и генератор случайных чисел. Других устройств нет.
- **Ядро гостя.** Мы загружаем ядро kuberoot для riscv64, которое переносится параллельно. Это жёсткое требование: Kubernetes нужны overlayfs, cgroup v2 и netfilter, а в ядре Linux 4.15 из комплекта TinyEMU поддержки overlayfs нет совсем.
- **Модель исполнения, которую продиктовал замер.** Ядро гостя работает в отдельном Web Worker в плотном цикле и никогда не уступает управление через `setTimeout`. Ввод с консоли, завершение дисковых операций и сетевые кадры приходят через кольцевые буферы в общей памяти, а флаг «есть события» проверяется раз в N инструкций. Инструкция WFI превращается в `Atomics.wait` с таймаутом до ближайшего срабатывания таймера. Замер показал, что TinyEMU проводит вне интерпретатора от 25 до 41 % времени из-за того, что уступает главный поток браузеру, и одно это изменение даёт ускорение примерно в 1,3–1,7 раза.
- **Проверка корректности.** Мы прогоняем riscv-tests (`rv64ui/um/ua/uf/ud/uc`, `rv64si/mi`) и riscv-arch-test через RISCOF с эталонной моделью Spike (лицензия BSD-3-Clause). Загрузку Linux сверяем с нашей исправленной сборкой TinyEMU, сравнивая трассы первых нескольких сотен миллионов инструкций.
- **Критерий успеха R1 из раздела 6.12.** Ядро kuberoot для riscv64 загружается до оболочки, riscv-arch-test проходит, а скорость интерпретатора на CoreMark во время работы не ниже, чем у TinyEMU (около 400 миллионов инструкций в секунду), и при этом нет потерь на уступание главного потока.

### R2. JIT-компиляция в WebAssembly

- **Уровни исполнения.** Интерпретатор считает входы в каждый базовый блок, а блок, в который вошли больше примерно 50 раз, ставится в очередь на трансляцию. Блоки наращиваются в суперблоки по линейному продолжению и по более частой ветке, но никогда не пересекают границу гостевой страницы, поэтому сбрасывать устаревший код можно постранично.
- **Пакетная трансляция.** Транслирует отдельный Web Worker-компилятор: он собирает горячие блоки и выпускает один модуль WebAssembly со многими функциями, потому что у компиляции и создания экземпляра модуля есть постоянная цена, и модуль на каждый блок обошёлся бы слишком дорого. Исполняющее ядро получает скомпилированный `WebAssembly.Module`, создаёт экземпляр поверх общей памяти и общей таблицы функций и обновляет свою карту блоков.
- **Устройство кода.** Внутри оттранслированной функции регистры гостя хранятся в локальных переменных WebAssembly: они загружаются при входе и записываются обратно при выходе и перед вызовом вспомогательных функций. Целочисленные инструкции RV64 переводятся в инструкции `i64` один к одному. Блок возвращает следующий адрес гостевой программы диспетчеру, а там, где браузер поддерживает хвостовые вызовы WebAssembly (`return_call` уже есть в текущих Chrome, Firefox и Safari), горячие блоки переходят друг в друга напрямую.
- **Быстрый путь TLB.** Программный TLB прямого отображения, например по 256–1024 записи отдельно для чтения, записи и выборки инструкций, хранит тег страницы и смещение до адреса в памяти хоста. Попадание стоит примерно шести-восьми инструкций WebAssembly и одной операции `i64.load` или `i64.store`. Промах, обращение к устройству или невыровненный доступ вызывают вспомогательную функцию, которая обходит таблицы Sv39 и заполняет запись. Страницы, на которых лежит уже оттранслированный код, вносятся в TLB записи как «медленные», поэтому запись в них перехватывается и сбрасывает блоки этой страницы. Так остаются корректными самоизменяющийся код и загрузка модулей ядра.
- **Точные исключения.** Каждая операция, которая может вызвать исключение, знает свой гостевой адрес ещё при трансляции. Вспомогательная функция записывает этот адрес перед тем, как вызвать исключение, и обновлять счётчик команд после каждой инструкции не нужно.
- **Прерывания.** Каждый блок уменьшает счётчик; когда счётчик доходит до нуля, блок возвращается в диспетчер, а тот проверяет ожидающие события.
- **Плавающая точка.** Обычный случай, то есть округление к ближайшему и отсутствие чтения флагов, исполняется встроенными операциями `f64` и `f32`. Упаковку NaN и накопление `fflags` обслуживают короткие проверки после операций, которые могут выставить флаги NV, OF, UF или NX, а динамический режим округления, отличный от RNE, уходит в программную реализацию. Программы Kubernetes в основном целочисленные, и этот путь для них не критичен, но он обязан давать точный результат.
- **Критерий успеха R2.** Ускорение относительно R1 и TinyEMU на CoreMark и на запуске kubectl и kube-apiserver. Цель задаёт столбец «нужное ускорение» в таблице выше.

### R3. Многопроцессорность и снимки

- **Ядра гостя в Web Worker.** Каждый виртуальный процессор работает в своём Web Worker с тем же кодом WebAssembly поверх одной общей `WebAssembly.Memory`, в которой лежат оперативная память гостя и отдельные TLB каждого ядра. Атомарные операции AMO переводятся в атомарные операции чтения-изменения-записи WebAssembly, пара LR/SC реализуется резервированием и сравнением с обменом, а `fence` становится `atomic.fence`. Межпроцессорные прерывания и удалённые сбросы TLB через SBI RFENCE передаются флагом в общей памяти и вызовом `Atomics.notify`. Простаивающее ядро спит в `Atomics.wait`, поэтому узел без нагрузки не тратит процессор ноутбука.
- **Общий кэш кода.** Скомпилированные модули рассылаются всем ядрам гостя, и каждое создаёт свой экземпляр один раз.
- **Снимки.** Снимок хранит регистры процессора, CSR, состояние устройств вместе с очередями virtio и оперативную память. При сборке образа узел загружается в Chromium без окна, как это уже делает `build-lab-snapshots.mjs` для v86, на нём запускается kuberoot, кэш страниц сбрасывается, и в снимок попадают только ненулевые страницы памяти, сжатые и разбитые на порции. **Ленивое восстановление:** на стороне ученика каждая страница памяти сначала отмечена в TLB как отсутствующая. Первое обращение к ней уходит на медленный путь, который останавливает ядро гостя в `Atomics.wait`, пока другой Web Worker скачивает и распаковывает нужную порцию. Узел начинает работать, как только пришли состояние процессора и устройств и первые несколько мегабайт памяти, и поэтому восстановление укладывается в пять секунд даже для гостя с 512 МБ памяти.
- **Критерий успеха R3 из раздела 6.12.** Узел kuberoot стартует из снимка не дольше чем за 5 с, а под запускается не дольше чем за 3 с.

### R4. Два узла kuberoot

- В одной вкладке работают две машины, у каждой одно-два ядра и не больше 512 МБ памяти, а соединяет их коммутатор `dt-switch` через virtio-net. Управляющий слой кластера работает на первом узле.
- Сеть подов строится на Flannel с VXLAN или на Cilium без ускорения eBPF, как сказано в разделе 6.12.
- **Критерий успеха.** Команда `kubectl apply` создаёт настоящие поды на обоих узлах, остановка одного узла переносит его поды на второй, а бюджет скорости из раздела 6.12 выдерживается на ноутбуке с 16 ГБ памяти.

## Как повторить замер

Все большие файлы складываются в `web/public/rv64-r0/`, и git их не отслеживает. Команды запускаются из каталога `web/`:

```bash
node src/engine/rv64-r0/fetch.mjs          # скачать, сверить sha256, распаковать (manifest.json)
bash src/engine/rv64-r0/build-tinyemu.sh   # собрать TinyEMU в wasm с правками R0
SLICE=30000000 bash src/engine/rv64-r0/build-tinyemu.sh   # вариант с большим отрезком исполнения
bash src/engine/rv64-r0/build-disk.sh      # собрать диск Alpine riscv64 с программами Kubernetes
node src/engine/rv64-r0/measure.mjs engine=r0 disk=alpine mem=1024 k8s=1
```

Страница `src/engine/rv64-r0/index.html` выполняет тот же сценарий вручную: её открывают через `npm run dev` по адресу `/src/engine/rv64-r0/index.html`, а из курса на неё ссылок нет. Использованные инструменты: Emscripten 6.0.9, Go 1.26.5, zig 0.17.1 как кросс-компилятор C для CoreMark, e2fsprogs 1.47.4 и Chromium 159 из Playwright.
