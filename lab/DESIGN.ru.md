# Локальная лаборатория: проект

[English version](DESIGN.md)

Курс работает в браузере, и большинству блоков больше ничего не нужно. Но на некоторых этапах нужны настоящие машины: экзамены по Linux и сетям проходят на машине, которую ученик администрирует сам, на этапе Kubernetes ученик ставит кластер руками через kubeadm, а следующим блокам (выкладка, GitOps, мониторинг, «Кластер из кода») нужен работающий кластер, в который можно выкладывать. Страницы экзаменов уже описывают эти машины как то, что заказывают в облаке. Локальная лаборатория даёт другой путь: `dtlab`, одна программа, которая запускает те же машины на компьютере ученика, раздаёт оттуда курс, чтобы всё работало без интернета, одним нажатием снимает с машин факты для экзамена и одной командой убирает всё это с компьютера.

## 1. Что запускается

| ВМ | Образ | Для чего | Размер по умолчанию |
|---|---|---|---|
| `learner` | облачный образ Ubuntu 24.04 minimal | экзамены по Linux и сетям на настоящей машине, а внутри лаборатории ещё и рабочее место ученика (kubectl для кластера kuberoot) | 1 vCPU, 1 ГиБ |
| `cp-1`, `worker-1`, `worker-2` | облачный образ Ubuntu 24.04 minimal, без предустановленного | этап 2 главы 05-kubernetes: containerd, kubeadm и Cilium ставит сам ученик | 2 vCPU, 2 ГиБ |
| `kr-1` | kuberoot `edge` (своё ядро, EFI-носитель из `mkimage`) | готовый кластер для блоков после этапа установки | 2 vCPU, 1,5–2,5 ГиБ |

Готовый кластер здесь kuberoot, а не k3s. Это один образ со своим ядром и своим init, им управляют через сам API Kubernetes (SSH у него нет), он проходит conformance, а с небольшой нагрузкой занимает около 0,5 ГиБ резидентной памяти (замеры в [README](README.ru.md)). Образ Ubuntu minimal (около 250 МБ на скачивание) нужен только там, где курсу требуется обычный Linux: для машины ученика и для узлов этапа kubeadm. На эти узлы ничего от Kubernetes не ставится заранее, потому что установка и есть то, чему учит этап. Семя cloud-init даёт им только то, что облако даёт новой машине: имя, SSH-ключ ученика, сеть и имена лаборатории в `/etc/hosts`.

## 2. Профили

Профиль задаёт размер всей лаборатории, а `--with` выбирает её части.

| Профиль | Компьютер | Части по умолчанию | Память ВМ |
|---|---|---|---|
| только браузер | 4 ГБ | нет | — |
| `light` | 8 ГБ, 2 ядра, 10 ГБ свободно | `learner` + `kr-1` или, с `--with kubeadm-nodes`, отдельно `cp-1` + `worker-1` | 2,3 ГиБ / 3,3 ГиБ |
| `standard` | 16 ГБ, 4 ядра, 20 ГБ свободно | `learner` + `kr-1` + `cp-1` + `worker-1` | 6,75 ГиБ |
| `full` | 24 ГБ, 6 ядер, 30 ГБ свободно | `learner` + `kr-1` + `cp-1` + `worker-1` + `worker-2` | 10 ГиБ |

В память компьютера входят операционная система и браузер с курсом, вместе около 4 ГБ. `dtlab check` смотрит на компьютер (система, процессор, память, свободная сейчас память, свободное место там, где живёт лаборатория, и какой гипервизор работает) и называет самый крупный подходящий профиль, а `dtlab up` без `--profile` берёт именно его. Экзамен k8s-2 просит три узла kubeadm. На компьютере с 16 ГБ это `--profile full --with kubeadm-nodes`, то есть три узла без машины ученика и без kuberoot, всего около 6,5 ГиБ.

## 3. Бэкенды

Лаборатория должна загружать образы двух разных видов на Windows 10/11, на macOS с процессорами Intel и Apple Silicon и на Linux. Первый вид — облачные образы Ubuntu, которые понимает любой инструмент. Второй — EFI-образ диска kuberoot со своим ядром, без cloud-init, SSH и гостевого агента, который сам устанавливается на второй диск и перезагружается в установленную систему.

**Lima** запускает произвольные образы через `vz` на macOS и через QEMU на Linux, но управляет машинами по SSH и через гостевой агент, который ставит cloud-init: от них зависят проброс портов, проверка готовности и общие папки. У kuberoot нет ни того, ни другого, поэтому Lima смогла бы его запустить, но не узнала бы, когда он готов, не пробросила бы его порты и не проследила бы за перезагрузкой после установки. Своего бэкенда для Windows у Lima тоже нет, там она работает внутри WSL2. **Multipass** на macOS и Windows загружает только образы Ubuntu, так что kuberoot ему не подходит. **Hyper-V** загружает оба вида (машина второго поколения берёт VHDX, сделанный из любого из образов), но он есть только в Windows Pro, Enterprise и Education, требует прав администратора, а у его внутренних коммутаторов нет DHCP. **QEMU** загружает оба образа везде, с ускорителем каждой системы: KVM на Linux, Hypervisor.framework на macOS (`-accel hvf`, x86_64 на Mac с Intel и aarch64 со сборкой kuberoot для arm64 на Apple Silicon) и Windows Hypervisor Platform на Windows (`-accel whpx`, есть и в редакциях Home). QEMU работает как обычный процесс ученика, root ему не нужен, и именно на нём проект kuberoot проверяет установку и обновления.

Поэтому лаборатория везде использует **QEMU**, а Hyper-V — только на Windows, где Windows Hypervisor Platform выключена, а Hyper-V включён:

| Компьютер | Бэкенд | Ускоритель | Почему |
|---|---|---|---|
| Linux | QEMU | KVM | родная скорость; ни демона, ни root, достаточно группы `kvm` |
| macOS, Apple Silicon | QEMU | HVF | загружает EFI-носитель kuberoot для arm64 и образы Ubuntu для arm64 |
| macOS, Intel | QEMU | HVF | то же с образами amd64 |
| Windows 10/11 с Windows Hypervisor Platform | QEMU | WHPX | те же ВМ, диски и сеть, что на других системах |
| Windows Pro только с Hyper-V | Hyper-V | — | ВМ второго поколения, Secure Boot выключен, диски VHDX |

`dtlab check` говорит, чего не хватает и как это поставить (`brew install qemu`, `apt install qemu-system-x86 qemu-utils ovmf`, `winget install SoftwareFreedomConservancy.QEMU`). Пакет лаборатории для macOS и Windows приносит QEMU с собой в `<корень>/backends/qemu` (QEMU распространяется по GPL, и вместе с пакетом идёт адрес его исходников) и записывает его в манифест как свой, поэтому uninstall его удаляет. QEMU, который стоял раньше, записывается как уже бывший, и без вопроса его не удаляют.

У Hyper-V есть два известных ограничения. Образ Ubuntu minimal загружает ядро `linux-kvm`, в котором нет драйверов дисков и сети Hyper-V, поэтому на Hyper-V лаборатория берёт полный серверный облачный образ того же выпуска, в ядре `virtual` которого они есть (у образа для Azure они тоже есть, но его cloud-init читает только метаданные Azure и не видит семя NoCloud). В ядро kuberoot с первого его выпуска встроены гостевые драйверы Hyper-V (диски и сеть VMBus, balloon, служебные сервисы, сокеты, синтетическое видео); диски там SCSI, поэтому лаборатория ставит его на `sda`, а не на `vda`. Если на Hyper-V ученика kuberoot всё же не загрузится, выход — Windows Hypervisor Platform (одна галочка в компонентах Windows и перезагрузка; существующий Hyper-V при этом продолжает работать) и QEMU.

Код бэкендов только собирает команды и передаёт их интерфейсу запуска. Модульные тесты сверяют точные командные строки QEMU и скрипты PowerShell с поддельным исполнителем, так что в тестах ни одна ВМ не запускается.

## 4. Сеть

У каждой ВМ одна сетевая карта в одной виртуальной сети `10.10.1.0/24`. Это частная сеть из уроков курса (`cp-1` в f-kubeadm имеет адрес `10.10.1.11`), так что команды из уроков работают без правок. Одна карта важна для kubeadm: если дать узлу вторую карту для интернета, kubelet возьмёт адрес маршрута по умолчанию, одинаковый `10.0.2.15` на всех узлах, и кластер сломается так, как курс не объясняет.

С QEMU сеть — это коммутатор в пространстве пользователя внутри процесса агента dtlab: [gvisor-tap-vsock](https://github.com/containers/gvisor-tap-vsock), та же сеть, что у podman machine на macOS и Windows. Каждый QEMU подключается к нему по TCP-сокету на loopback (`-netdev socket,connect=127.0.0.1:7789`). Шлюз коммутатора `10.10.1.1` по DHCP выдаёт каждой ВМ постоянный адрес (статическая аренда по MAC), отвечает на DNS-запросы об именах лаборатории (`cp-1.lab`, `kr-1.lab`, `host.lab`), остальные пересылает дальше и через сокеты самого компьютера выпускает трафик в интернет. Адрес `10.10.1.254` — это компьютер, каким его видят ВМ: он отображается на `127.0.0.1` компьютера, и так ВМ достают до агента. Компьютер достаёт до ВМ через порты, которые коммутатор публикует только на `127.0.0.1`: `2210`–`2223` для SSH, `50000` для API узла kuberoot, `6443` для его API-сервера, `6444` для API-сервера kubeadm. Один и тот же код без изменений работает на трёх системах, ему не нужны ни root, ни мост, ни TAP-устройство, и когда агент останавливается, на компьютере ничего не остаётся.

С Hyper-V сеть — это внутренний коммутатор `dtlab`, у компьютера на нём адреса `10.10.1.1` и `10.10.1.254`, а в интернет трафик уходит через NetNat. Своего DHCP у внутреннего коммутатора нет, поэтому на нём отвечает агент лаборатории (`10.10.1.1:67`): каждая ВМ по своему MAC получает постоянный адрес, компьютер в роли маршрутизатора и публичные DNS-серверы. ВМ с Ubuntu вдобавок несут адрес в `network-config` своего семени. Карта у каждой ВМ и здесь одна, и от Default Switch, которого в Windows Server нет, ничего не зависит. Компьютер обращается к ВМ по их собственным адресам (SSH на 22, API узла на 50000, API-сервер на 6443), а не через опубликованные порты, а агент для ВМ слушает ещё и `10.10.1.254:7788`, причём его API отвечает только на loopback. Правило брандмауэра `dtlab-lab` пропускает ВМ через брандмауэр Windows только на коммутаторе лаборатории и удаляется вместе с ним.

## 5. Как настраивается каждая ВМ

ВМ с Ubuntu читают семя NoCloud. С QEMU семя — не диск: серийный номер SMBIOS машины содержит `ds=nocloud;s=http://10.10.1.254:7788/seed/<vm>/`, и cloud-init при первой загрузке берёт `meta-data` и `user-data` у агента. С Hyper-V семя — образ ISO с меткой `CIDATA`, который записывает встроенный в Windows интерфейс создания образов, так что отдельная программа для ISO не нужна. Системный диск — это qcow2-надстройка над образом из кэша, поэтому ВМ занимает место только под свои изменения, а новая ВМ ничего не скачивает. SSH-ключ у лаборатории свой (`<корень>/config/id_ed25519`), ключи ученика не используются, а ключи машин записываются в собственный `known_hosts` лаборатории.

kuberoot настраивается через свой API установки. dtlab записывает загрузочный носитель программой `mkimage` из kuberoot с каталогом доверия этой лаборатории (`<корень>/config/kuberoot-trust`). Носитель несёт CA, выпущенный для этой лаборатории, и до API узла доходит только её административный сертификат. ВМ загружается с пустым системным диском первым и носителем вторым, и пустой диск передаёт загрузку носителю. dtlab ждёт API узла на `127.0.0.1:50000`, создаёт `Installation` на `vda` с `reboot: true`, ждёт, пока загруженный слот станет `Good`, и берёт у API узла административный kubeconfig кластера (`kubeconfigs/admin`). Одну копию он кладёт для компьютера (`<корень>/config/kuberoot.kubeconfig`, сервер `127.0.0.1:6443`, имя для TLS — адрес узла), другую — в машину ученика (`~/.kube/config`, сервер `10.10.1.30:6443`). Это тот же порядок, что в собственном сквозном тесте kuberoot на QEMU.

## 6. Раздача курса

Агент раздаёт собранный курс (`web/dist`, который `dtlab up --course` или `dtlab serve --course` копирует в `<корень>/course`, чтобы лаборатория не зависела от исходников) по адресу `http://127.0.0.1:7788/` с теми же заголовками `Cross-Origin-Opener-Policy` и `Cross-Origin-Embedder-Policy`, что и в `vite.config.ts`: без них не работает Linux в браузере. Курс — это PWA, и после первой загрузки он и так работает без сети, а из лаборатории он работает и на компьютере, который после установки лаборатории ни разу не выходил в интернет.

## 7. Факты с машин

Страницы экзаменов на настоящих машинах (`web/src/app/real/`) дают ученику скрипт проверки, который только читает, и поле для блока, который он печатает. Лаборатория использует оба скрипта без изменений. dtlab хранит копии `web/public/check/trainer-check.sh` и `web/src/app/real/trainer-check-host.sh` (тест падает, если они разошлись с курсом), запускает скрипт по SSH, передавая его текст на стандартный ввод, так что на диск ВМ ничего не пишется, и возвращает блок между `-----BEGIN TRAINER ...-----` и `-----END TRAINER ...-----`. Что запускать, зависит от ВМ. На машине ученика это проверка машины от root. На узле kubeadm — проверка кластера с `--machine` от root и с `KUBECONFIG=/etc/kubernetes/admin.conf`. У kuberoot нет оболочки, поэтому проверку его кластера запускают на машине ученика с её kubeconfig. Аргументы самого экзамена (`--scope net`, `--file /etc/hosts`, `--tcp web,10.10.1.21,80`) передаются как есть.

`dtlab facts <vm>` печатает блок. `POST /api/v1/facts` агента возвращает его странице курса, а `web/src/engine/locallab/client.ts` — это сторона страницы: `detectLab()` находит запущенную лабораторию, `collectFacts()` возвращает блок для уже существующего декодера экзамена (`decodeHostBlob`), а `vmForMachine()` сопоставляет машину экзамена с ВМ лаборатории. Дальше страница экзамена оценивает блок точно так же, как вставленный руками.

## 8. Безопасность

Всё слушает только loopback: агент (`127.0.0.1:7788`), коммутатор (`127.0.0.1:7789`), каждый опубликованный порт ВМ и мониторы QEMU. Из сети ученика до лаборатории не достать. Агент отклоняет запросы, у которых `Host` не его собственный (защита от DNS rebinding), отвечает на API только странице, которую раздаёт сам, или источнику, названному в `--allow-origin`, и требует в каждом вызове API заголовок `X-DTLab`, который не умеют отправлять формы и картинки. Вызовы API из ВМ агент отклоняет: ВМ получают только свои семена, скрипты проверки и файловый кэш. Запросы фактов проверяются (одноразовый код, имена машины и трека, длина аргументов, отсутствие переводов строки), а каждый аргумент экранируется для удалённой оболочки. API узла принимает только клиентский сертификат этой лаборатории, а носитель и каталог доверия kuberoot создаются для каждой лаборатории заново и удаляются вместе с ней.

## 9. Без интернета

Всё скачанное лежит в `<корень>/cache`: образ Ubuntu (сверенный с `SHA256SUMS`), артефакты kuberoot и `mkimage` (из выпуска kuberoot на GitHub — последнего или названного в `--kuberoot-version`; каждый файл сверяется с sha256 из `kuberoot-edge.json` выпуска и хранится под своей версией), а также `kubectl` для машины ученика, который она сначала берёт у агента и только потом из интернета. После первого `dtlab up` команды `dtlab destroy` и снова `dtlab up` сеть не используют. Каждый источник можно направить на зеркало или локальный каталог (`--kuberoot <адрес или каталог>` или `DTLAB_KUBEROOT_URL`, `DTLAB_UBUNTU_URL`), и так в классе одну загрузку раскладывают на все компьютеры: каталог с файлами выпуска и его манифестом сверяется так же, как загрузка, а раскладка собственной сборки (`<arch>/`, `bin/`) берётся как есть. Без сети выпуск заменяет манифест, сохранённый при последней загрузке того же выпуска. То, что ученик ставит внутри ВМ (пакеты apt, kubeadm, образы контейнеров), по-прежнему идёт из интернета. Для блоков с кластером это снимет запланированный локальный реестр (§11).

## 10. Остановка и удаление

Три команды, простыми словами:

- `dtlab down` останавливает ВМ и агента. Диски и работа ученика остаются, и `dtlab up` продолжит с того же места.
- `dtlab destroy` удаляет ВМ, их диски, учётные данные kuberoot этой лаборатории и её сеть на компьютере. Скачанные образы остаются, поэтому следующий `up` быстрый и начинается с чистых машин.
- `dtlab uninstall` убирает всё, что лаборатория когда-либо добавила: ВМ и диски, образы и кэши, сеть, копию курса, настройки и состояние, бэкенды, которые поставил dtlab, строки в PATH и автодополнение, а последней — саму программу dtlab.

Удаление здесь — полноценная функция, а не приложение. Все данные лаборатории лежат в одном каталоге на каждой системе (`~/.dtlab` на Linux и macOS, `%LOCALAPPDATA%\dtlab` на Windows, а `DTLAB_HOME` переносит его в другое место). Всё, что dtlab создаёт за пределами своего процесса, в момент создания записывается в `<корень>/manifest.json`: каталоги, путь к программе, строки PATH (ровно тот текст, что был добавлен), файлы автодополнения, ВМ Hyper-V, коммутатор и NAT, бэкенды с отметкой, были ли они на компьютере до dtlab. `uninstall` печатает список с размерами, спрашивает подтверждение (или принимает `--yes`), останавливает ВМ, удаляет записи по порядку (ВМ, сети, бэкенды, данные, строки PATH и последней программу), а потом проверяет каждую запись заново и сообщает, осталось ли что-нибудь и сколько места освободилось. О том, что было на компьютере до dtlab, например о QEMU из Homebrew или о Hyper-V самого ученика, спрашивают отдельно, и по умолчанию это остаётся. Корневой каталог удаляется даже тогда, когда манифест повреждён или потерян, поэтому в худшем случае останется только строка в PATH, и отчёт её назовёт. На Windows запущенная программа не может удалить сама себя, поэтому её удаляет отдельный `cmd` через мгновение после выхода dtlab. Страница курса показывает те же три команды с теми же объяснениями (`LAB_REMOVAL` в `client.ts`).

## 11. Что ещё не сделано

- **Локальный git-сервер и реестр.** Блокам GitOps и CI нужны git-сервер и реестр контейнеров, до которых достаёт кластер. План — запускать оба как пакеты в кластере kuberoot (Soft Serve или Gitea и zot) с данными на диске kuberoot, чтобы `destroy` и `uninstall` удаляли их вместе с ВМ, а образы для работы без сети раздавать из архива, который агент отдаёт как зеркало реестра только для чтения. Не реализовано.
- **Встраивание в страницу экзамена.** `client.ts` готов и покрыт тестами, но в панели экзамена (`web/src/app/real/panel.ts`) ещё нет кнопки «Снять факты из лаборатории» рядом с каждым полем для блока.
- **Hyper-V и WHPX** проверены на Windows Server 2025 во вложенной ВМ, на ноутбуке ученика с Windows 11 — ещё нет. Остаются два ограничения: QEMU под WHPX не может сбросить ВМ, в которой уже поработал Linux («WHPX: Unexpected VP exit code 4»), поэтому лаборатория запускает QEMU с `-action reboot=shutdown`, а агент слушает второй монитор и запускает ВМ снова, если гость перезагрузился; NetNat у Hyper-V не урезает размер TCP-сегмента, поэтому за выходом в сеть с MTU меньше 1500 TLS из ВМ может зависать (чтобы лаборатория могла это исправить, kuberoot должен брать MTU из DHCP).
- **QEMU в комплекте** для macOS и Windows спроектирован (каталог, запись в манифесте), но не упакован. Сейчас dtlab берёт QEMU из PATH.
