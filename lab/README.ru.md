# dtlab: локальная лаборатория DevOps-тренажёра

[English version](README.md) · [Проект](DESIGN.ru.md)

`dtlab` запускает машины курса на вашем компьютере: Linux-машину для экзаменов по Linux и сетям, чистые узлы Ubuntu, на которых вы собираете Kubernetes через kubeadm, и готовый кластер kuberoot для блоков о выкладке, GitOps и мониторинге. Оттуда же он раздаёт курс, чтобы всё работало без интернета, за один шаг снимает с машин факты для экзамена и одной командой убирает всё это с компьютера.

## Установка

Скачайте установщик со страницы [последнего выпуска](https://github.com/damn-academy/devops-trainer/releases/latest). Установщики и каталог курсов появятся там после публикации; если установщика для вашей системы ещё нет, скачайте отдельный файл программы. Для чтения установленного курса QEMU не нужен: он требуется для виртуальных машин лаборатории.

### Windows

Скачайте `dtlab-windows-amd64.msi`, откройте его и следуйте шагам установки. Программа установится в `Program Files\dtlab`, а установщик добавит этот каталог в PATH. После установки откройте новое окно терминала.

Установщик не подписан. Если SmartScreen показывает «Windows protected your PC», убедитесь, что файл скачан из этого репозитория, нажмите «More info», затем «Run anyway». Если организация запретила эту кнопку, обратитесь к её администратору. Подробнее об этом предупреждении написано в [документации Microsoft](https://learn.microsoft.com/windows/apps/package-and-deploy/smartscreen-reputation).

Вместо установщика можно скачать `dtlab-windows-amd64.exe`, переименовать его в `dtlab.exe` и выполнить в PowerShell `.\dtlab.exe install`.

### macOS

Для Mac с Apple Silicon, начиная с M1, скачайте `dtlab-darwin-arm64.pkg`, а для Intel — `dtlab-darwin-amd64.pkg`. Откройте пакет и следуйте шагам установки; программа установится в `/usr/local/bin/dtlab`.

Пакет не подписан. Если Gatekeeper сообщает «unidentified developer», сначала попробуйте открыть пакет, затем перейдите в «Системные настройки» → «Конфиденциальность и безопасность», найдите сообщение о заблокированном пакете и нажмите «Всё равно открыть». Подтвердите открытие и введите пароль. Так вы разрешите запуск этого пакета, сохранив защиту Gatekeeper. Этот порядок описан в [инструкции Apple](https://support.apple.com/en-us/102445).

Вместо установщика можно скачать отдельный файл программы для своего процессора, переименовать его в `dtlab`, выполнить `chmod +x dtlab`, затем `./dtlab install`.

### Linux

Для Intel и AMD выберите `amd64`, для ARM — `arm64`. В Debian и Ubuntu скачайте `dtlab-linux-amd64.deb` и выполните `sudo apt install ./dtlab-linux-amd64.deb`. В Fedora и RHEL скачайте `dtlab-linux-amd64.rpm` и выполните `sudo dnf install ./dtlab-linux-amd64.rpm`. На ARM замените `amd64` на `arm64`. Пакеты устанавливают программу в `/usr/bin/dtlab`.

В остальных дистрибутивах запустите скрипт: он определит процессор, скачает программу, проверит SHA256 и установит её в `~/.local/bin`:

```sh
curl -fsSL https://github.com/damn-academy/devops-trainer/releases/latest/download/install.sh | sh
```

Добавьте каталог в PATH командой `export PATH="$HOME/.local/bin:$PATH"` и сохраните эту строку в файле запуска своей оболочки. Для установки всем пользователям скачайте `install.sh` и выполните `sh install.sh --system`: скрипт вызовет sudo и установит программу в `/usr/local/bin`.

Вместо скрипта можно скачать `dtlab-linux-amd64` или `dtlab-linux-arm64`, переименовать файл в `dtlab`, выполнить `chmod +x dtlab`, затем `./dtlab install`.

### Проверка контрольной суммы

Скачайте `SHA256SUMS` из того же выпуска, что и установщик. В Linux выполните `sha256sum dtlab-linux-amd64.deb`, в macOS — `shasum -a 256 dtlab-darwin-arm64.pkg`, а в PowerShell — `Get-FileHash .\dtlab-windows-amd64.msi -Algorithm SHA256`. Подставьте имя скачанного файла и сравните всю полученную сумму со строкой для этого файла в `SHA256SUMS`. При загрузке курсов программа сама проверяет размер и SHA256 по каталогу.

## Курсы

Чтобы скачать курс и открыть локальный сайт, выполните:

```sh
dtlab courses
dtlab course install academy
dtlab serve
```

Откройте http://127.0.0.1:7788/. Команда `courses` показывает пакеты со статусами `available`, `installed` и `update`, а также курсы в базовом пакете. Команда `dtlab course install v86` добавляет файлы Linux-машин, которые работают во вкладке, и сама устанавливает необходимый пакет `academy`. Пакет `rv64` появляется в каталоге, когда сборка содержит его файлы. В одной команде установки можно указать несколько пакетов.

Команда `dtlab course update` обновляет все установленные пакеты. Программа скачивает и проверяет файлы до переключения активного набора, а предыдущие версии сохраняет на диске. Команда `dtlab course remove v86` удаляет все версии этого пакета. Перед удалением `academy` удалите пакеты, которые от него зависят. Перед удалением пакетов остановите локальный сервер, а после обновления перезапустите его.

Курсы хранятся в `~/.dtlab/courses/<id>/<version>` на Linux и macOS или в `%LOCALAPPDATA%\dtlab\courses\<id>\<version>` на Windows. Общий каталог сайта использует жёсткие ссылки, поэтому образы машин не занимают место второй раз. Команды `dtlab serve` и `dtlab up` сами выбирают установленный курс, если вы не передали другой каталог через `--course`. Без установленных курсов команды работают как раньше. Команда `up` запускает виртуальные машины лаборатории и затем печатает адрес локального курса.

Для зеркала задайте полный адрес каталога в `DTLAB_CATALOG_URL`, например `https://mirror.example/releases/catalog.json`; архивы должны лежать рядом. Переменная `DTLAB_HOME` меняет каталог данных. Ошибка сети не мешает читать уже установленный курс. Каталог `.lock` запрещает одновременное изменение курсов; после аварийного завершения удаляйте его только тогда, когда убедились, что другие команды установки не работают.

Команда `dtlab uninstall` удаляет курсы вместе с данными лаборатории. Если программа установлена системным пакетом, команда сохраняет исполняемый файл и печатает команду удаления пакета: `sudo apt remove dtlab`, `sudo dnf remove dtlab` или `msiexec /x` с кодом установленного продукта. В macOS команда имеет вид `sudo rm /usr/local/bin/dtlab && sudo pkgutil --forget academy.damn.dtlab`: сначала удаляется файл, затем запись об установке. После удаления данных Linux-установку через `install.sh --system` удаляют командой `sudo rm /usr/local/bin/dtlab`.

## Как начать

```sh
dtlab check                          # что может этот компьютер
dtlab up                             # профиль, который посоветовал check
dtlab up --profile standard --course web/dist
dtlab status
dtlab ssh learner
dtlab ssh cp-1                       # собирайте кластер, как на этапе 2 главы о Kubernetes
kubectl --kubeconfig ~/.dtlab/config/kuberoot.kubeconfig get nodes
```

После этого курс открывается по адресу <http://127.0.0.1:7788/>. Сеть лаборатории — `10.10.1.0/24`, частная сеть из уроков: `learner` — `10.10.1.10`, `cp-1` — `10.10.1.11`, `worker-1` — `10.10.1.21`, `worker-2` — `10.10.1.22`, `kr-1` — `10.10.1.30`, и машины знают друг друга по этим именам. На узлах kubeadm ничего от Kubernetes не установлено: это ваша работа на этапе. На машине ученика есть `kubectl` и kubeconfig для кластера kuberoot.

На Linux сначала поставьте QEMU (`sudo apt install qemu-system-x86 qemu-utils ovmf` в Debian и Ubuntu) и состойте в группе `kvm`. На macOS — `brew install qemu`. На Windows — `winget install SoftwareFreedomConservancy.QEMU` (или установщик с qemu.weilnetz.de, на который ссылается qemu.org; dtlab находит QEMU в `Program Files\qemu`, в PATH его добавлять не нужно) и включённая платформа низкоуровневой оболочки Windows (компоненты Windows, затем перезагрузка).

## Факты для экзамена

Экзамены на настоящих машинах просят запустить на машине скрипт проверки, который только читает, и вставить напечатанный им блок. В лаборатории оба шага делает `dtlab facts`:

```sh
dtlab facts cp-1 --nonce <код со страницы экзамена>           # k8s-2: проверка кластера на cp-1
dtlab facts learner --nonce <код> --machine app-01 --track linux-disk --arg '--scope mounts'
dtlab facts kr-1 --nonce <код>                               # кластер kuberoot, с машины ученика
```

Команда печатает тот же блок, который вы вставили бы руками. Страница курса, которую раздаёт `dtlab`, может запросить его сама (`POST /api/v1/facts`, см. `web/src/engine/locallab/client.ts`).

## Как остановить и удалить лабораторию

| Команда | Что делает | Что остаётся |
|---|---|---|
| `dtlab down` | Останавливает машины и освобождает их память. | Всё: диски машин и ваша работа на них. `dtlab up` продолжит с того же места. |
| `dtlab destroy` | Удаляет машины и их диски. | Скачанные образы, чтобы следующий `dtlab up` создал чистые машины без новой загрузки. |
| `dtlab uninstall` | Убирает всё, что лаборатория когда-либо добавила на компьютер: машины и диски, образы и кэши, сеть лаборатории, копию курса, настройки и состояние, гипервизор, если его поставил сам dtlab, строки, добавленные в файл запуска вашей оболочки, и саму программу dtlab. | Ничего от лаборатории. То, что было на компьютере до dtlab (QEMU, который вы ставили сами, ваш Hyper-V), остаётся, если вы не скажете иначе. |

`dtlab uninstall` сначала показывает список того, что удалит, с размерами, и спрашивает подтверждение; `--yes` отвечает за вас. После удаления он заново всё проверяет и сообщает, сколько места освободилось и не осталось ли чего-нибудь. Все данные лаборатории лежат в одном каталоге — `~/.dtlab` на Linux и macOS и `%LOCALAPPDATA%\dtlab` на Windows, — так что удаление этого каталога убирает лабораторию, даже если что-то пошло не так.

## Сборка

```sh
cd lab
go test ./...
GOFLAGS=-p=2 CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -ldflags "-s -w" -o dtlab ./cmd/dtlab
```

dtlab собирается для linux/amd64, linux/arm64, darwin/amd64, darwin/arm64 и windows/amd64 (12–14 МБ каждая сборка). Тесты не запускают ни одной ВМ: бэкенды только собирают команды, а тесты сверяют их с поддельным исполнителем.

## Состояние

От начала до конца работает на Linux с KVM: `check`, `up` со всеми частями, `status`, `ssh`, `facts` (из командной строки и через API), `serve`, `down`, снова `up`, `destroy`, `install`, `uninstall`. На Windows (Windows Server 2025, та же основа 24H2, что у Windows 11, в ВМ с вложенной виртуализацией, 4 vCPU и 5 ГиБ) `check`, `up --profile light`, `status`, `ssh`, `facts`, перезагрузка внутри ВМ и `uninstall` работают и с Windows Hypervisor Platform, и с Hyper-V: лёгкая лаборатория поднялась за 5 мин 44 с на QEMU с WHPX и за 2 мин 8 с на Hyper-V, где kuberoot грузится со своими драйверами Hyper-V и ставится на `sda`; после `uninstall` реестр, PATH, Hyper-V и сеть остались такими, как были. Пока нет: локального git-сервера и реестра, кнопки «снять факты из лаборатории» на странице экзамена, автоматического прогона на macOS (законно запустить macOS в тестовом кластере нельзя, проверка ручная, см. ниже) и QEMU в комплекте. Известное на Windows: QEMU под WHPX не умеет сбросить ВМ, в которой уже поработал Linux, поэтому перезагрузка выключает QEMU, а агент лаборатории запускает его снова; у Hyper-V NAT пропускает пакеты как есть, и на компьютере, чей выход в сеть меньше 1500 по MTU (VPN, PPPoE), TLS из ВМ может зависать, а у коммутатора лаборатории на QEMU такого нет. kuberoot берётся из его выпуска на GitHub (последнего или `--kuberoot-version 1.2.3`) со сверкой по манифесту выпуска; `--kuberoot <адрес или каталог>` вместо этого берёт зеркало, копию выпуска или сборку. Подробнее в [DESIGN.ru.md](DESIGN.ru.md), §11.

## Ручная проверка на macOS и настоящей Windows 11

Автоматический прогон на macOS невозможен (macOS нельзя законно запустить в тестовом кластере), поэтому чек-лист проходится вручную. 26.11.2026 его прошли на MacBook с Apple M4, 16 ГБ и macOS 26.4.1: `check` нашёл Hypervisor.framework и посоветовал `light`; `up --profile light` скачал образы arm64 и поднял лабораторию за 1 мин 40 с, повторный `up` после `down` — за 14 с; `status`, `ssh learner`, `kubectl get nodes` (узел Ready), под nginx, `facts kr-1`, `down` и `uninstall --yes` отработали, `uninstall` освободил 1,9 ГиБ и ничего не оставил, QEMU из Homebrew остался на месте. Windows проверялась в виртуальной машине, и пока чек-лист не пройден на настоящей Windows 11, её поддержка — «должно работать». Нужен один компьютер, 30–40 минут и 10–20 ГБ диска.

1. `dtlab check` — нашёл QEMU и Hypervisor.framework (macOS) или платформу низкоуровневой оболочки Windows (Windows 11: компонент Windows, затем перезагрузка); посоветовал профиль.
2. `dtlab up --profile light` — машина ученика и `kr-1` загрузились, kuberoot установился на диск (в выводе видно слот Good).
3. `dtlab status` — все машины зелёные.
4. `dtlab ssh learner` — вход без пароля; `ping kr-1` с машины ученика отвечает.
5. `kubectl --kubeconfig ~/.dtlab/config/kuberoot.kubeconfig get nodes` — узел Ready.
6. Курс в браузере: `dtlab serve --course web/dist`, открыть <http://127.0.0.1:7788/>, пройти урок с машиной; кнопка снятия фактов на странице экзамена видит лабораторию.
7. Перезагрузка изнутри: на `kr-1` выполнить `reboot` — узел снова становится Ready. На Windows с WHPX это выглядит как остановка QEMU и его повторный запуск агентом — известное поведение, не ошибка.
8. `dtlab down`, затем `dtlab up` — машины и вся работа на них на месте.
9. `dtlab destroy`, потом `dtlab uninstall --yes` — диск освободился, в `~/.dtlab` (`%LOCALAPPDATA%\dtlab` на Windows) ничего не осталось.
10. На Windows с основным интерфейсом MTU меньше 1500 (VPN, PPPoE) проверить с машины ученика `curl -v https://github.com` — TLS не должен зависать (NAT Hyper-V пропускает пакеты как есть).

Результаты записывать в [STATUS](../web/STATUS.ru.md): версия ОС, длительность шага 2, отклонения.
